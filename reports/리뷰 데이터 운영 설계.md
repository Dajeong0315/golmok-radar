# 리뷰 데이터를 안전하게 두 흐름으로 엽니다

결론부터 말하면, **네이버·구글·카카오 지도 화면을 크롤링해 경쟁점 리뷰를 자동 수집하는 구현은 Phase 17의 완료 경로가 될 수 없습니다.** 현재 확인된 공개 API와 약관으로는 경쟁점 원문 리뷰를 장기 저장·AI 분석·익명 집계할 권한이 확보되지 않았고, 상호를 A/B/C로 바꾸어도 수집과 재사용 권한 문제가 해소되지 않습니다. 대신 이 기능은 `내 가게 운영 점검`과 `상권 탐색용 익명 집계`라는 두 제품 흐름으로 설계하되, 전자는 사업주가 권한을 가진 공식 API 또는 내보내기 파일, 후자는 분석·저장·익명 집계를 명시적으로 허용한 계약 데이터 제공자만 연결해야 합니다. 권한이 없는 동안에는 실제 리뷰 대신 권한 게이트와 가상 데이터(fixture)만 사용해 화면·계산·삭제 흐름을 검증하는 것이 맞습니다. 이렇게 하면 나중에 공급자가 정해져도 수집 어댑터만 교체해 두 흐름을 안전하게 열 수 있고, 골목 레이더의 ‘추천·성공 단정 금지’ 원칙도 지킬 수 있습니다.

## 크롤링이 아니라 권한이 Phase 17의 시작점입니다

Google의 공식 Places API는 Place Details에서 사용자 리뷰를 최대 5개까지 돌려줄 수 있지만, Places 콘텐츠의 사전 수집·캐싱·저장은 제한하며 지도 밖 표시에는 귀속·링크 요건도 둡니다. 따라서 이를 여러 경쟁점에서 모아 자체 주제 분석 데이터셋으로 축적하는 것은 적합하지 않습니다. Google Business Profile API는 OAuth로 연결된 **검증된 본인 매장**의 리뷰를 관리하는 경로이고, 콘텐츠 사용에도 별도 제한이 따릅니다. ([Places API 정책](https://developers.google.com/maps/documentation/places/web-service/policies), [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details), [Business Profile 리뷰 API](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list))

네이버도 사전 허가·명시적 허용·합법적 API 범위 밖의 자동 수집을 금지하며, 공개 개발자 API 목록에는 플레이스 리뷰 API가 없습니다. 카카오 로컬 API는 장소 검색·주소·좌표·경로를 제공하지만 리뷰 본문·별점·작성일 필드는 제공하지 않습니다. 즉 네이버·카카오의 웹 화면 HTML이나 비공개 호출을 자동화하는 방식은 제외해야 합니다. ([네이버 서비스 운영정책](https://policy.naver.com/policy/disclaimer.html), [네이버 API 목록](https://developers.naver.com/products/intro/plan/plan.md), [카카오 로컬 API](https://developers.kakao.com/docs/ko/local/dev-guide))

가명 처리도 권한의 대체물이 아닙니다. A/B/C는 경쟁점 식별 노출을 줄이는 **표시 방식**일 뿐, 원문을 수집·보관·분석·재배포할 법적·계약상 근거를 만들지 않습니다. 그러므로 현재 문서의 정책처럼 Google·네이버·카카오 크롤링은 계속 금지하고, 계약서 또는 API 약관에 `분석`, `저장 기간`, `파생 집계`, `화면 표시`, `삭제 전파`, `출처 표기`가 모두 명시된 제공자만 Phase 17 데이터 어댑터로 허용해야 합니다.

## 상권 탐색과 운영 점검은 같은 원천, 다른 질문입니다

상권 탐색에서는 사용자가 공식 상권과 업종을 고르면, 같은 업종·같은 공식 상권의 적격 매장 리뷰를 **개별 매장 대신 그룹 집계**로 보여줍니다. 초기 지표는 ‘자주 언급된 주제’, ‘긍정·개선 요청 언급 비율’, ‘분석 대상 매장 수·리뷰 수·기간·제외 수’로 제한합니다. 이는 고객이 무엇을 언급하는지 살피는 맥락 정보이며, 상권의 우열·창업 성공·매출을 예측하는 점수는 아닙니다.

운영 점검에서는 사용자가 본인 소유 또는 관리 권한이 확인된 매장을 연결하거나 권한 있는 내보내기 파일을 올립니다. 최근 90일의 내 가게 주제 변화와 같은 조건의 익명 비교군 분포를 나란히 보되, 비교군이 권한·표본 기준을 충족할 때만 제공합니다. 이때 ‘비슷한 타깃’은 추정하지 않습니다. 공급자가 제공하거나 사용자가 확인 가능한 매장 유형·서비스 유형 필드가 있을 때만 필터에 쓰고, 없으면 같은 업종·같은 공식 상권·유사한 리뷰 기간과 리뷰 규모까지만 사용합니다. 상권 데이터의 경계는 임의 반경이 아니라 기존 `trade_area_code`를 우선 적용하며, 인접 상권 확장은 사용자의 명시적 선택일 때만 허용합니다.

두 흐름은 원천·보관·근거 체계를 공유하되 결과는 분리합니다. 상권 화면은 개인 매장과 개별 경쟁점을 드러내지 않는 집계만, 내 가게 화면은 내 가게의 시계열과 가명 비교군을 보여줍니다. 비교군 가명은 서버에서 `provider_place_id`로만 관리하고 매 조회마다 안정적이지 않은 A/B/C를 부여합니다. 화면에는 상호·정확 좌표·원문 인용·정확 리뷰 수를 조합해 재식별할 수 있는 정보를 내보내지 않습니다.

## 12개월 창과 보수적 표본선으로 시작합니다

초기 기본 기간은 **최근 12개월**로 정하고, 최근 90일과 91~365일을 분리해 표시합니다. 카페의 계절성을 숨기지 않으면서 최근 변화도 읽을 수 있는 구성입니다. 허가된 계약 데이터의 경쟁점·상권 집계는 **30일마다 증분 수집**을 기본으로 하고, 내 가게는 공급자 약관과 API 한도에서 허용되면 **주 1회 증분 수집**을 선택지로 둡니다. 이 주기는 제품 권고안일 뿐이며 제공자별 TTL·삭제·갱신 조건이 더 엄격하면 계약 조건이 항상 우선합니다.

초기 공개 기준은 텍스트 리뷰가 있는 매장 하나당 기간 내 **20건 이상**, 그중 최근 90일 **5건 이상**입니다. 상권 집계는 적격 매장 **5곳 이상 및 텍스트 리뷰 총 100건 이상**, 운영 비교군의 분포 표시는 적격 매장 **3곳 이상 및 총 60건 이상**을 요구합니다. 이 숫자는 통계적 진실을 보증하는 임계값이 아니라 소수 리뷰를 과대해석하거나 한 매장을 사실상 드러내지 않기 위한 제품 안전선입니다. 실제 계약 데이터의 리뷰 분포와 제공자 최소 집계 단위를 확인한 뒤 조정합니다.

기준 미달이면 0이나 빈 그래프를 보여주지 않습니다. 예를 들어 “최근 12개월 적격 매장 3곳·텍스트 리뷰 46건으로 기준(5곳·100건)을 충족하지 않아 비교할 수 없습니다”라고 기간, 분자·분모, 제외 이유를 밝힙니다. 사용자는 24개월까지 기간 확장, 인접 공식 상권 포함, 내 가게 추세만 보기를 직접 선택할 수 있지만 서비스가 자동으로 범위를 넓혀 결과를 만들지는 않습니다. 적격 매장이 5곳 미만이면 A/B/C 카드도 숨기고 그룹 중앙값·범위처럼 재식별 위험이 낮은 집계만 제공합니다.

## 데이터 계약과 단계적 공개가 구현 순서를 결정합니다

첫 단계는 공급자별 권한 표입니다. 제공자·계약/약관 버전·허용 목적·원문 저장 여부·AI 처리·파생 집계·표시 및 귀속 조건·호출 한도·TTL·삭제/정정 전파·감사 요구를 모두 승인 상태로 관리하고, 하나라도 미확정이면 어댑터가 네트워크 호출을 하지 않도록 차단합니다. 현재 진행 중인 제휴 문의는 실제 서면 회신 전에는 이를 충족하지 않으므로, 답변을 받은 뒤 동일 기준으로 검토해야 합니다.

권한이 확인되면 카페 업종 10곳 이하의 단일 공급자 파일럿으로 시작합니다. 원천 레코드는 `provider`, `provider_place_id`, `provider_review_id`, `business_id`, `trade_area_code`, `industry_code`, `published_at`, `rating`, `text_or_tokenized_payload`, `source_url`, `license_basis_id`, `fetched_at`, `updated_at`, `expires_at`, `deleted_at`, `content_hash`를 갖고, `(provider, provider_review_id)`를 중복 키로 둡니다. 원문 보관이 허용되지 않으면 텍스트 대신 공급자가 허용한 토큰화 또는 집계 결과만 저장하며, 원문이 필요한 AI 분석은 아예 실행하지 않습니다. 분석 결과는 `topic_key`, `sentiment_label`, `model_version`, `prompt_version`, `analysed_at`, `unknown/exclusion_reason`을 보관해 재현성과 오류 추적을 보장합니다.

공개 순서는 권한 게이트와 fixture, 파일럿 수집·TTL·삭제, 상권 익명 집계, 마지막으로 A/B/C 운영 비교군입니다. 각 카드에는 공급자·권한 근거·수집/갱신 시각·분석 기간·적격/제외 건수·최소 기준·보관 상태·분석 및 집계 규칙 버전을 보여 주고, 권한 미확정·표본 부족·수집 실패·보관 만료는 각각 다른 사유로 `준비 중` 또는 `비교 불가`를 반환합니다.

## Phase 17은 허가 경로를 검증할 때 완료됩니다

구현 전 사용자와 결정해야 할 항목은 세 가지입니다. 첫째, 첫 공급자를 계약 API로 할지, 내 가게 소유자 제공 내보내기 파일로 할지입니다. 둘째, 내 가게의 소유·관리 권한을 Google OAuth, 공급자 사업자 인증, 파일 업로드 확인 중 무엇으로 검증할지입니다. 셋째, 계약상 가능한 주제 분류 체계와 텍스트/파생값의 보관 기간입니다. 이 결정을 하지 않으면 실제 리뷰 어댑터는 만들지 않고 fixture만 유지합니다.

완료 조건은 ‘크롤러가 돈다’가 아니라, 권한이 승인된 경로만 호출되고 삭제·TTL·중복·부분 실패·rate limit이 안전하게 처리되며 각 인사이트의 근거를 사용자가 검증할 수 있는 상태입니다. 테스트는 권한 없는 제공자 차단, 페이지네이션·중복·정정·삭제·TTL, 상권/업종 연결 오류, 20·60·100건과 3·5곳 경계, 기간 확장 동의, 가명 재식별 방지, 계정 A/B 격리, PC와 360px 화면을 포함해야 합니다. 제공자 계약이 없는 오늘의 다음 작업은 이 권한 게이트·공통 스키마·fixture 기반 화면·테스트를 구현하고, 실제 외부 리뷰 수집은 서면 권한 이후로 분리하는 것입니다.

## Conclusion

이 기능의 경쟁력은 많은 리뷰를 긁는 데 있지 않고, **어떤 리뷰를 어떤 권한과 기간으로 묶었는지 설명할 수 있는 데** 있습니다. 상권 탐색은 익명 집계로 수요 신호를 읽고, 운영 점검은 내 가게의 변화와 조건이 맞는 비교군을 분리해 읽으면 두 목적을 한 데이터 계약 위에서 충돌 없이 제공할 수 있습니다. 권한 게이트를 먼저 완성하면 제휴가 늦어져도 제품의 신뢰성과 구현 진척을 동시에 확보할 수 있습니다.
