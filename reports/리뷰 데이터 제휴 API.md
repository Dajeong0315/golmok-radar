# 서울 카페 리뷰 제휴를 안전하게 확보한다

골목 레이더가 내 가게와 주변 경쟁 카페의 리뷰를 합법적으로 자동 수집·분석하려면 **식신 MetaDex와 다이닝코드에 동일한 B2B 제안서를 동시에 보내고, Tripadvisor Terra로 서울 카페 커버리지 PoC를 병행하는 전략**이 가장 현실적이다. 공개 문서만으로 원문 제공·자동 분석·파생지표 저장·화면 표시 권리를 모두 확정한 공급자는 아직 없으므로, “API 제공”이라는 설명만 믿고 개발해서는 안 된다. 식신과 다이닝코드는 자체 리뷰와 제휴 활용 근거, 데이터 문의 창구가 함께 확인돼 국내 1차 협상 후보로 적합하다. Terra는 스크래핑이 아닌 Tripadvisor의 정식 UGC 콘텐츠 API이며 주변 장소 검색과 리뷰 원문을 제공하지만, 서울 독립 카페의 실제 매칭률과 계약상 파생분석 권리는 표본으로 확인해야 한다. 카카오·네이버는 계속 장소 검색과 매칭에만 사용하고, 리뷰 원문은 별도의 라이선스 공급원에서 받아야 한다. 계약 전에는 공급사가 원천별 재허락 권리, 경쟁점 제공 권리, 삭제 동기화, 분석·표시 범위를 서면으로 증명해야 하며, 하나라도 증명하지 못하면 탈락시켜야 한다.

## 국내 두 후보와 Terra를 동시에 검증한다

**1순위 국내 후보는 식신 MetaDex**다. 식신은 리뷰·블로그 기반 정성 데이터 마이닝, 맞춤 데이터 제공, API 연동을 공식적으로 안내하고 있으며, 이용약관에는 회사 또는 허락된 제3자가 식신 리뷰를 제휴 서비스에서 필요한 범위로 표시·편집·복제·전송·배포할 수 있다는 근거가 있다. 이는 골목 레이더가 자동으로 사용권을 얻는다는 뜻은 아니지만, 별도 B2B 데이터 계약을 논의할 실질적 기반이 있음을 의미한다. 특히 식신의 데이터 서비스에는 웹 수집 데이터가 섞일 가능성도 있으므로, 계약 대상은 **식신 회원이 직접 작성한 자체 리뷰 또는 재라이선스 권리를 문서로 입증한 원천**으로 제한해야 한다. ([식신 AI 데이터 서비스](https://alipay.siksinhot.com/aidata), [식신 이용약관](https://www.siksinhot.com/static2/html/siksinhot/service.html))

**다이닝코드는 식신과 같은 날 제안서를 보낼 2순위 후보**다. 다이닝코드는 공식 사이트에 `contact@diningcode.com`을 데이터 제휴 문의처로 공개하고, 약관에서 Open API 서비스를 정의하며 회원 리뷰를 회사 사업 관련 제3자에게 필요한 범위로 복제·전송·전시·배포할 수 있다고 밝힌다. 다만 공개 API 명세, 가격, 서울 카페 커버리지, 원문·요약 제공 범위는 공개되지 않았다. 따라서 “다이닝코드 회원 직접 작성 리뷰”와 외부 블로그·제3자 콘텐츠를 원천 코드로 분리해 달라고 요구하고, 전자는 별도 라이선스 계약으로만 사용해야 한다. ([다이닝코드 데이터 제휴](https://www.diningcode.com/profile.php?rid=eDOEEXwuxAez), [다이닝코드 이용약관](https://www.diningcode.com/policy.service.php))

**Tripadvisor Terra는 해외 정식 UGC API 중 가장 유력한 실증 후보**다. Terra의 리뷰 API는 제목·본문·평점·방문 맥락·사업주 답변을 반환하고 한국어와 원문 언어 조회를 지원한다. Nearby API는 좌표·반경으로 식당을 찾을 수 있고, Tripadvisor는 이 콘텐츠가 직접 제출된 리뷰라고 설명한다. 첫 1,000회 호출을 무료로 제공하므로 계약 협상 전 커버리지 표본을 만들기 좋다. 반면 Tripadvisor에 등록되지 않은 서울 카페는 조회할 수 없고, 원문 보관 기간·파생 분석 결과의 소유·LLM 입력·삭제 SLA는 공개 문서가 아니라 계약으로 확정해야 한다. ([Terra 리뷰 API](https://docs.terra.tripadvisor.com/reference/locationreviewsget), [Terra Nearby API](https://docs.terra.tripadvisor.com/reference/cataloglocationsnearbyget), [지원 언어](https://docs.terra.tripadvisor.com/docs/supported-languages-for-reviews), [Terra 소개와 무료 호출](https://www.tripadvisor.com/business/solutions/hotels/terra-content-api-bottom))

레드테이블은 레스토랑 DaaS 역량과 공식 문의처가 확인되지만 공개 상품에서 리뷰 원문은 확인되지 않아 자격 확인용 3순위다. Yelp Insights는 최근 최대 200개 리뷰 원문을 제공하는 정식 분석 API지만 Yelp 공식 로케일에 한국이 없어 서울 주 데이터원으로 보기 어렵다. Google Business Profile은 인증된 본인 매장 리뷰에는 쓸 수 있지만 경쟁점에는 사용할 수 없다. DataForSEO·Outscraper·SerpApi는 기술적으로 리뷰를 빠르게 가져오더라도 원천 플랫폼의 분석·재표시 권리를 보증하는 정식 콘텐츠 라이선스가 확인되지 않으므로 이번 조달에서 제외한다. ([레드테이블 기관 소개](https://www.bigdata-culture.kr/bigdata/user/data_market/agency/detail.do?id=redtable_org), [Yelp Insights](https://docs.developer.yelp.com/docs/yelp-insights), [Yelp 지원 로케일](https://docs.developer.yelp.com/docs/resources-supported-locales), [Google Business Profile 리뷰](https://developers.google.com/my-business/content/review-data))

| 접촉 순서 | 공급자 | 지금 확인된 가치 | 계약 전 확인하지 못한 핵심 |
| --- | --- | --- | --- |
| 병행 1 | 식신 MetaDex | 국내 음식점·리뷰 데이터 사업, API·맞춤 데이터 안내 | 서울 카페 커버리지, 자체 리뷰 비율, 원문·파생분석·표시권, 가격 |
| 병행 1 | 다이닝코드 | 데이터 제휴 창구, 자체 회원 리뷰, Open API 근거 | 공개 명세·가격, 경쟁점 원문 제공 범위, 삭제 피드 |

## 원천 권리 하나라도 불명확하면 구매하지 않는다

공급사 선정은 가격 비교보다 **권리 하드 게이트**가 먼저다. 공급사는 원천별로 리뷰에 접근할 권리뿐 아니라 상업 서비스에서 자동 분석하고, 감성·주제·빈도 같은 파생지표를 만들고, 허용된 발췌와 원문 링크를 표시하고, 정해진 기간 저장하며, 골목 레이더에 그 권리를 재허락할 수 있음을 계약서로 보증해야 한다. “공개 데이터”, “정식 API”, “자체 수집” 같은 표현은 이 권리를 대신하지 못한다. Google Maps 약관이 콘텐츠의 스크래핑·저장·복사·파생 콘텐츠 생성을 제한하고, Places 정책이 리뷰 표시 시 저자 귀속과 원문 링크를 요구하는 점은 공급사의 API 접근권과 고객의 재사용권이 서로 다르다는 대표 사례다. ([Google Maps Platform 약관](https://cloud.google.com/maps-platform/terms), [Google Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies))

계약은 리뷰마다 `provider`, `source_platform`, `source_place_id`, `source_review_id`, `source_url`, `created_at`, `updated_at`, `collected_at`, `language`, `rating`, `text`, `deleted_at`을 받을 수 있게 해야 한다. 리뷰 삭제·수정은 tombstone, webhook 또는 안정적인 증분 조회로 전파돼야 하며, 계약 종료 시 원문·백업·로그와 식별 가능한 파생물을 언제 삭제하는지 명시해야 한다. 원문은 계약이 허용하는 최소 기간만 암호화해 보관하고, 초기 MVP에서는 모델 학습에 사용하지 않는다. 공급사가 외부 LLM이나 번역 서비스를 쓴다면 업체명, 처리 국가, 전송 필드, 보존기간, 학습 사용 여부를 하위처리자 목록으로 공개해야 한다.

개인정보 처리 위탁이나 국외이전이 발생할 수 있으므로 DPA에는 처리 목적, 데이터 유형, 처리지역, 보존·파기, 하위처리자, 접근통제, 침해 통지, 정보주체 요청 지원을 포함해야 한다. 국내 개인정보 보호법은 위탁계약 문서화와 안전조치를 요구하고 국외이전에 별도 요건을 두고 있으므로, 최종 계약은 국내 개인정보·저작권·플랫폼 전문 변호사의 검토를 받아야 한다. 이는 법률 자문을 대체하는 보고서가 아니다. ([개인정보 보호법 제26조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335321), [개인정보 보호법 제28조의8](https://www.law.go.kr/lsInfoP.do?lsiSeq=283839))

## 2주 PoC로 서울 카페 적합성을 먼저 증명한다

계약 전 PoC는 **서울 5개 자치구에서 카페 100곳을 층화 표본**으로 고르는 방식이 적절하다. 각 구에서 프랜차이즈 10곳과 독립 카페 10곳을 카카오 공식 장소 검색으로 선정하고, 공급사 ID와 주소·좌표·전화·영업상태를 매칭한다. 화면 자동 수집은 하지 않으며, 공급사가 허용한 API·샘플과 사람의 제한적 확인만 사용한다. 사용자가 한 매장을 선택했을 때 반경 500m 내 같은 업종 3곳을 거리순으로 구성하고, 최근 6개월 리뷰를 요청하는 흐름을 동일하게 시험한다. 카카오 공식 API는 장소 이름·카테고리·주소·좌표·상세 URL·거리를 제공하지만 리뷰 원문은 제공하지 않으므로 장소 발견과 매칭 역할에만 유지한다. ([카카오 로컬 API](https://developers.kakao.com/docs/ko/local/dev-guide))

권고 내부 합격선은 장소 매칭률 80% 이상, 공급사 ID 중복 1% 미만, 폐업·이전 오매칭 2% 미만, 매칭된 장소 중 최근 6개월 한국어 텍스트 리뷰 보유율 60% 이상이다. 이는 공개 통계가 아니라 골목 레이더가 PoC 전에 정할 제품 기준이므로, 실제 예산과 데이터 분포를 보고 조정할 수 있다. 리뷰 한 건마다 원천·시각·언어·평점·삭제 상태가 빠짐없이 들어오는지 검사하고, 동일 cursor 재호출, pagination, `updated_since`, 429와 `Retry-After`, 재시도 중복, 삭제 이벤트를 계약 테스트로 만든다. 원문은 PoC 요청 동안만 메모리 또는 짧은 TTL 저장소에서 처리하고, 파생지표도 계약이 허용하기 전에는 운영 DB에 남기지 않는다.

제품은 카카오 장소 ID와 공급사 장소 ID를 직접 덮어쓰지 말고 별도 매핑 테이블로 관리해야 한다. 최소 필드는 `kakao_place_id`, `provider`, `provider_place_id`, 주소 정규화값, 좌표, 매칭 신뢰도, 검토 상태, 확인 시각이다. 리뷰 수집기는 서버에서만 공급사 키를 읽고 timeout, schema 검증, 최대 길이, HTML 이스케이프, 재시도 상한, circuit breaker와 월 호출 예산을 적용한다. 프론트엔드는 원문 API를 직접 호출하거나 비밀키를 보유하지 않는다. 공급자가 삭제 이벤트를 제공하지 않으면 권장 polling 주기와 삭제 지연 SLA를 서면으로 받고, 재조회에서 사라진 리뷰의 원문과 식별 가능한 파생 결과를 함께 지우는 테스트가 필요하다.

가격은 월 고정비만 묻지 말고 장소 수·리뷰 수·호출 수·갱신 빈도·backfill·webhook·초과요금·최소 약정·종료 비용을 같은 표로 받아야 한다. 공급사에는 1천·1만·5만 장소를 월 1회·4회·30회 갱신하는 아홉 시나리오의 월 예상비용과 최대비용을 요청한다. Terra는 공개 쿼터와 무료 호출이 있지만 엔터프라이즈 가격은 견적형이고, 식신과 다이닝코드도 공개 가격이 없으므로 공개 가격끼리 비교할 수 없다. ([Terra 호출 한도](https://docs.terra.tripadvisor.com/docs/rate-limits))

## 같은 RFP로 세 공급사의 답을 비교한다

아래 문안을 식신 문의 양식, 다이닝코드 `contact@diningcode.com`, Tripadvisor Terra 영업 문의에 같은 날 보낸다. 레드테이블에는 먼저 리뷰 원문 보유와 재라이선스 가능 여부만 확인하고, 통과할 때 동일 RFP를 보낸다. 문의 발송은 외부 커뮤니케이션이므로 담당자명·법인명·연락처·예상 트래픽과 함께 사용자가 최종 확인한 뒤 진행해야 한다.

```text
제목: [데이터 제휴 문의] 서울 카페 경쟁점 리뷰 API 및 분석 이용권

안녕하세요. 서울에서 첫 카페 창업을 준비하는 사용자를 위한 상권 분석 서비스
‘골목 레이더’입니다.

사용자가 자신의 가게를 선택하면 반경 500m 안의 동종 카페 3곳을 자동으로 구성하고,
양쪽 리뷰를 메뉴·가격·응대·대기·청결·공간 주제로 비교하는 기능을 준비하고 있습니다.
화면 스크래핑이나 비공개 엔드포인트는 사용하지 않으며, 정식 API와 계약상 이용권이
확인된 데이터만 사용하려고 합니다.

다음 자료와 30분 미팅 가능 일정을 요청드립니다.

1. 서울 카페 장소·리뷰 커버리지, 자체 작성 리뷰와 외부 원천의 비율,
   업데이트 주기와 평균·최대 지연
2. 장소 검색·매칭, 주변 동종 업종 조회, 리뷰 원문·증분·삭제 API 문서와
   개인정보를 제거한 샘플 응답
3. 경쟁점 리뷰 본문 접근, 서버 임시 저장, 자동 주제·감성 분석,
   파생지표·요약 보관, 제한적 발췌 표시, 작성자 귀속·원문 링크,
   상업적 이용과 계약 종료 후 처리의 허용 범위
4. 원천별로 위 권리를 제공·재허락할 수 있다는 확인과 필수 표시·보존 조건
5. pagination, rate limit, webhook·삭제 통지, 버전·폐기 정책, SLA와 지원 체계
6. DPA, 처리 국가·리전, 하위처리자와 외부 AI 사용, 고객 데이터의 모델 학습 여부,
   보안 인증·침투시험·침해사고 통지 정책
7. 서울 카페 100곳을 대상으로 한 2주 샌드박스 PoC 가능 여부와,
   1천·1만·5만 장소를 월 1회·4회·30회 갱신할 때의 가격,
   최소 약정·초과·backfill·종료 비용

가능하다면 API 명세(OpenAPI), 원천별 권리 요약, DPA·하위처리자 목록,
가격표와 서울 카페 샘플을 부탁드립니다. 회신 자료는 내부 제품·보안 검토와
외부 법률 검토에 사용됩니다.

감사합니다.
골목 레이더 / 담당자명 / 법인명 / 연락처
```

회신을 받으면 먼저 하드 게이트를 적용한다. 모두 통과한 후보만 서울 카페 커버리지·최신성 25점, 장소 매칭 20점, 리뷰 완전성·한국어 품질 15점, API 운영성 15점, 보안·개인정보 10점, SLA·지원 5점, 총소유비용·계약 유연성 10점으로 평가한다. 100점 중 75점 이상이면서 커버리지와 장소 매칭 영역이 각각 배점의 60% 이상인 후보만 최종 협상에 남기는 기준이 합리적이다. 이 점수와 PoC 합격선은 조달을 시작하기 전 내부 결정으로 고정해 공급사별로 유리하게 바꾸지 않는다.

## Conclusion

이번 기능의 병목은 API 코딩이 아니라 **리뷰 원천의 권리 체인과 서울 카페 커버리지**다. 국내 사용자 적합성을 위해 식신·다이닝코드의 자체 리뷰 계약을 최우선으로 확인하고, Terra를 독립적인 정식 UGC PoC 기준선으로 사용하면 “국내 커버리지”와 “계약·기술 성숙도”를 동시에 비교할 수 있다. 공급사가 권리를 증명하기 전에는 실데이터 adapter를 만들지 말고, 현재 카카오 장소 자동 선택 뒤에 공급자 인터페이스와 fixture 계약 테스트만 유지하는 것이 안전하다.

가장 빠른 다음 행동은 세 후보에 동일 RFP를 발송해 **서울 카페 100곳 샘플, 권리 매트릭스, API 명세, DPA, 가격표**를 받는 것이다. 그 답변이 도착하면 골목 레이더의 Phase 17을 공급자 중립 adapter가 아니라 실제 계약 스키마에 맞춰 완성할 수 있다.
