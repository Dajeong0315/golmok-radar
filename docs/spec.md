# 골목 레이더 SPEC

> 범위 구분: 소개형 홈·마이페이지·비로그인 60분 미활동 만료·계정 이관의 계약은 12절, 완료 기록은 plan.md Phase 23~28에 있습니다. 기존 영구 localStorage 저장·초기 화면 정책은 확장 범위에서 대체했습니다. 완료된 전체 업종 확대 계약은 13절입니다. 앞 절의 카페 수치는 최초 MVP 구현 당시의 고정 범위를 기록합니다.

> 이 문서는 완료된 상권 탐색·비교 엔진의 구현 계약입니다. 신규 성향 진단·조건 기반 후보 탐색·임대·자금·리뷰·매물 검증 워크시트 기능은 기존 계약을 깨지 않고 `docs/product_v2_pipeline.md`의 별도 Phase로 확장합니다. Phase 19 워크시트는 V2의 별도 기능이며, 이 문서의 상권 비교 API·지표·계산 계약을 변경하지 않습니다.

## 1. 목적과 적용 범위

이 문서는 `docs/mvp.md`, `docs/prd.md`, `docs/프로젝트_결정사항_v2.md`를 구현 가능한 규칙으로 구체화합니다. 범위는 서울 25개 자치구의 공식 상권을 지도와 목록에서 탐색하고, 관심 목록에 저장한 상권 중 2~4곳을 비교하는 프로토타입입니다.

구현 전에 이 문서의 **확정 필요** 항목을 결정하거나, 해당 지표를 화면에서 `비교 불가`로 처리해야 합니다.

## 2. 기술 구성

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 프론트엔드 | React + TypeScript (Vite) | 상권 탐색·관심 목록, 2~4개 상권 비교, 근거 보기 |
| 백엔드 | Python + FastAPI | 데이터 조회와 계산형 지표 산출 |
| 운영 데이터베이스 | Supabase PostgreSQL | 정규화한 상권·지표·근거 데이터 저장 |
| 테스트 데이터베이스 | SQLite | 백엔드 자동 테스트 격리 |
| 마이그레이션 | Alembic | 운영 스키마 변경 이력 관리 |
| 지도 | 카카오맵 JavaScript API | 상권 위치·경계 표시 |

계산 로직은 프론트엔드가 아니라 백엔드에 둡니다. API 키와 DB 연결 정보는 `.env` 파일에만 보관하고, 저장소에는 `.env.example`만 둡니다.

## 4. 원천 데이터 계약

### 4.1 점포-상권 (2025)

원천 파일: `database/raw/store/서울시 상권분석서비스(점포-상권)_2025년.zip`의 CSV(CP949)

| 원천 컬럼 | 정규화 컬럼 | 용도 |
| --- | --- | --- |
| `stdr_yyqu_cd` | `quarter_code` | 기준분기 |
| `trdar_se_cd` | `area_type_code` | 상권 구분 코드 |
| `trdar_se_cd_nm` | `area_type_name` | 상권 구분명 |
| `trdar_cd` | `trade_area_code` | 상권 코드 |
| `trdar_cd_nm` | `trade_area_name` | 상권명 |
| `svc_induty_cd` | `industry_code` | 업종 코드 |
| `svc_induty_cd_nm` | `industry_name` | 업종명 |
| `stor_co` | `store_count` | 카페 점포 수 |
| `opbiz_rt` | `opening_rate` | 개업률 |
| `clsbiz_rt` | `closing_rate` | 폐업률 |

`similr_induty_stor_co`는 유사업종 점포 수이므로, MVP의 “카페 점포 수”에는 사용하지 않습니다.

### 4.2 추정매출-상권 (2025)

원천 파일: `database/raw/sales/서울시 상권분석서비스(추정매출-상권)_2025년.zip`의 CSV(CP949)

| 원천 컬럼 | 정규화 컬럼 | 용도 |
| --- | --- | --- |
| `기준_년분기_코드` | `quarter_code` | 기준분기 |
| `상권_코드` | `trade_area_code` | 상권 코드 |
| `상권_코드_명` | `trade_area_name` | 상권명 |
| `서비스_업종_코드` | `industry_code` | 업종 코드 |
| `당월_매출_금액` | `sales_amount` | 화면의 카페 추정매출 원천값 |
| `당월_매출_건수` | `sales_count` | 건당 평균 결제액의 분모 |
| `주중_매출_금액` | `weekday_sales_amount` | 주중 매출 |
| `주말_매출_금액` | `weekend_sales_amount` | 주말 매출 |

원천 컬럼명 `당월_매출_*`는 데이터 제공 정의를 확인해 MVP 화면에는 **카페 추정매출**로 표시합니다. 개인·법인 합계 외의 성별·연령별 세부 매출은 MVP에서 사용하지 않습니다.

### 4.3 영역-상권

원천 파일: `database/raw/area/서울시 상권분석서비스(영역-상권).zip`의 SHP·DBF(UTF-8, EPSG:5181)

- `TRDAR_CD`를 상권 코드로 사용합니다.
- 자치구와 상권명, 중심좌표 또는 경계를 후보 목록·지도에 사용합니다.
- 지도에 보낼 좌표는 WGS84로 변환합니다.
- 통계 데이터에만 있고 영역 데이터에 없는 상권은 후보에 넣지 않습니다.

### 4.4 길단위인구-상권

수집 방법: `database/scripts/fetch_population.py`로 서울 열린데이터광장 Open API를 원본 그대로 저장합니다.

인구 데이터 흐름은 다음과 같이 고정합니다.

```text
서울 열린데이터광장 Open API
  → database/raw/population/ 원본 CSV·수집 메타데이터
  → 적재·검증 스크립트
  → Supabase 지표 테이블
  → FastAPI 비교 API
  → React 화면
```

화면이나 FastAPI 요청마다 서울 Open API를 직접 호출하지 않습니다. 외부 API 장애·응답 지연·데이터 변경으로 비교 결과가 흔들리는 것을 막고, 화면의 숫자를 원본 파일과 수집 시점 기준으로 다시 검증할 수 있게 하기 위함입니다.

`SEOUL_OPEN_API_KEY`는 `backend/.env`에서만 읽습니다. 수집 스크립트는 API 키를 출력·저장·응답에 포함하지 않습니다. 원본 CSV와 함께 저장하는 메타데이터에는 서비스명, 수집 시각, 응답 총 행 수, 저장 행 수, 기준분기 컬럼과 범위만 기록합니다.

2026-10-29 수집 결과 서비스명은 `VwsmTrdarFlpopQq`, 저장 행 수는 36,281건이며 API 보고 행 수와 일치합니다. 기준분기 범위는 `20211~20262`이고 목표 분기 `20254`가 포함됩니다.

| 원천 컬럼 | 정규화 컬럼 | 용도 |
| --- | --- | --- |
| `STDR_YYQU_CD` | `quarter_code` | 기준분기 |
| `TRDAR_CD` | `trade_area_code` | 상권 코드 |
| `TRDAR_CD_NM` | `trade_area_name` | 상권명 |
| `TOT_FLPOP_CO` | `total_population` | 총 유동인구 |
| `TMZON_00_06_FLPOP_CO` 등 6개 | 시간대별 인구 컬럼 | 시간대별 유동인구 분포 |

길단위인구는 원천에 `STDR_YYQU_CD`가 있는 분기 데이터이므로 월간 값을 별도로 합계·평균하지 않습니다.

## 5. 정규화와 적재 규칙

### 5.1 공통 키

점포·매출 지표의 논리 키는 다음과 같습니다.

```text
quarter_code + trade_area_code + industry_code
```

상권 자체의 논리 키는 `trade_area_code`입니다. 인구 데이터는 원천 확인 후 같은 상권 코드와 기준기간을 키로 사용할 수 있는지 검증합니다.

### 5.2 적재 처리

1. 원천 파일은 수정하지 않고 `database/raw/`에 보관합니다.
2. 적재 스크립트는 CP949 CSV를 읽고 원천 컬럼을 정규화 컬럼으로 매핑합니다.
3. `quarter_code=20254`, `industry_code=CS100010`, 서울 25개 자치구 상권 코드로 필터링한 결과를 확인합니다.
4. 필터 결과의 행 수·중복 키·결측 필수값을 검증합니다.
5. 검증을 통과한 행만 서비스용 테이블에 적재합니다.
6. 수집일·원천 파일명·행 수·검증 결과를 `docs/data_sources.md`에 기록합니다.

### 5.3 적재 실패 처리

- 필수 컬럼이 없거나 중복 키가 있으면 적재를 실패로 처리합니다.
- 원천 행이 없는 상권·업종·분기는 값을 만들지 않습니다.
- 매출 행이 없는 상권은 매출과 그 매출 기반 계산 지표를 `비교 불가`로 표시합니다.
- 원천 컬럼 변경은 매핑 코드와 테스트를 수정한 뒤에만 허용합니다.

## 6. 지표 계산 명세

### 6.1 원천값 지표

| 화면 지표 | 원천값 | 단위 | 계산 |
| --- | --- | --- | --- |
| 카페 점포 수 | `store_count` | 개 | 없음 |
| 개업률 | `opening_rate` | % | 없음 |
| 폐업률 | `closing_rate` | % | 없음 |
| 카페 추정매출 | `sales_amount` | 원 | 없음 |

원천값은 화면 단위로만 보기 좋게 표기할 수 있으며, 근거 보기에는 원래 숫자와 표시 단위를 함께 제공합니다.

### 6.2 계산형 지표

| 지표 | 수식 | 표시 규칙 |
| --- | --- | --- |
| 주말 매출 비중 | `weekend_sales_amount / sales_amount × 100` | 분모가 0 또는 누락이면 비교 불가 |
| 주중 매출 비중 | `weekday_sales_amount / sales_amount × 100` | 분모가 0 또는 누락이면 비교 불가 |
| 건당 평균 결제액 | `sales_amount / sales_count` | 분모가 0 또는 누락이면 비교 불가 |
| 시간대별 유동인구 분포 | `time_slot_population / total_population × 100` | 인구 원천 계약 확정 후 구현 |

- 백엔드는 원본 정밀도로 계산하고, 화면은 소수 첫째 자리까지 반올림합니다.
- 원 단위의 금액은 정수로 표시하고, `건당 평균 결제액`도 원 단위로 반올림합니다.
- 계산식의 분자·분모·반올림 방식은 근거 보기에 노출합니다.

### 6.3 인구의 분기 처리

`STDR_YYQU_CD=20254`인 원천 행의 `TOT_FLPOP_CO`와 시간대별 인구 값을 그대로 사용합니다. 같은 상권·분기에 행이 없으면 인구 관련 지표를 `비교 불가`로 표시합니다.

지도 선택 근거는 상권 단위 통계만 사용합니다. 원천에는 거리·도로 단위 좌표 유동량이나 연령대별 유동인구가 없으므로, 지도 열지도·거리별 색상·연령대 분포로 표시하거나 추정하지 않습니다.

## 7. API 명세

모든 응답은 JSON을 사용합니다. API는 계산 실패를 0으로 바꾸지 않습니다.

| 메서드·경로 | 목적 | 성공 응답 핵심 |
| --- | --- | --- |
| `GET /api/v1/industries?quarter=20254` | 검증·적재 완료 업종 목록 조회 | 업종 코드, 업종명 |
| `GET /api/v1/trade-areas?industry={code}` | 탐색 가능한 상권 목록 조회 | `trade_area_code`, `name`, `district`, `area_type`, `latitude`, `longitude`, 업종별 `data_status` |
| `GET /api/v1/trade-areas/{code}` | 상권 기본 정보 조회 | 상권 코드, 이름, 구, 구분, 지도 정보 |
| `GET /api/v1/trade-areas/{code}/map-insight?industry={code}` | 지도 선택 근거 조회 | 같은 기준분기의 상권 단위 유동·선택 업종 매출·시간대 비중·동일 자치구 상대 위치와 결측 사유 |
| `GET /api/v1/comparisons?codes={code1},{code2}[,{code3},{code4}]&quarter=20254` | 2~4개 상권 비교 | 기준분기, 선택 상권 배열, 지표 배열 |
| `GET /api/v1/comparisons/{comparison_id}/evidence/{metric_key}` | 지표 근거 조회 | 출처, 원천값, 필터, 계산식, 상태 |
| `GET /api/v1/field-checklist` | 현장 확인 질문 조회 | 질문 배열, 분류, 안내 문구 |

### 7.1 비교 응답의 지표 구조

각 지표는 선택한 상권별 값을 배열로 반환합니다.

```json
{
  "metric_key": "weekend_sales_ratio",
  "label": "주말 매출 비중",
  "unit": "%",
  "values": [
    { "trade_area_code": "3120052", "status": "available", "value": 34.2 },
    { "trade_area_code": "3120053", "status": "unavailable", "value": null, "reason": "매출 원천 행이 없습니다." }
  ]
}
```

`status`는 `available`, `unavailable`, `pending_verification` 중 하나입니다. `unavailable`과 `pending_verification`의 `value`는 반드시 `null`입니다.

### 7.2 입력 검증과 오류

- `codes`에는 서로 다른 상권 코드가 2~4개 있어야 합니다.
- 상권 코드가 1개 이하이거나 5개 이상이면 400으로 응답합니다.
- 탐색 범위에 없는 상권 코드는 404로 응답합니다.
- 지원하지 않는 분기는 400으로 응답합니다.
- 서버 내부 오류는 원천 비밀값을 포함하지 않는 오류 메시지로 응답합니다.

## 8. 화면 동작 명세

### 8.1 상권 목록·지도와 관심 목록

- 상권 카드와 지도 마커는 같은 데이터를 사용합니다.
- 축소 지도에서는 가까운 핀을 상권 개수 원으로 묶습니다(지도 레벨 5 이상, 80px 격자). 원을 누르면 확대되며 상세 확대에서는 개별 핀을 표시합니다. 이름 라벨은 선택한 상권에만 표시합니다. 묶음 숫자는 상권 개수이며 통계 지표를 재집계하지 않습니다.
- 지도 마커를 클릭하면 해당 상권을 선택하고 지도 근거 카드를 갱신합니다. 관심 저장은 카드의 별표로 별도로 수행합니다.
- 목록의 상권 카드를 선택하면 해당 상권만 지도에 표시하고, 지도 중심과 확대 수준을 그 위치에 맞춥니다. 선택된 카드는 목록과 지도 라벨에서 함께 강조합니다.
- 카드에는 상권명, 자치구, 상권 구분을 표시합니다.
- 카드에는 점포·선택 업종 매출·유동인구 원천 행의 보유 여부를 각각 표시합니다. 0이나 "있음/없음" 두 항목으로 단순화하지 않습니다.
- 업종 선택기는 검증·적재가 끝난 업종만 노출합니다. 다른 업종은 원천 컬럼·공통 키·기준분기 검증 및 적재 뒤에 자동으로 선택할 수 있으며, 적재 전 수치를 만들지 않습니다.
- 지도 또는 카드에서 관심 상권을 추가·해제할 수 있습니다.
- 관심 상권 코드는 브라우저 `localStorage`의 `golmok-radar:favorites:v1` 키에 JSON 배열로 저장합니다.
- 저장된 코드 중 현재 API 상권 목록에 없는 코드는 화면 로드 시 제거합니다.
- 관심 목록에서 서로 다른 2~4곳을 선택해야 비교 화면으로 이동할 수 있습니다.
- 다섯 번째 상권을 선택하면 기존 선택은 바꾸지 않고 최대 네 곳이라는 안내를 표시합니다.
- 카카오맵 JavaScript 키는 `VITE_` 접두사의 프론트엔드 환경 변수로만 주입합니다.

### 8.2 2~4개 상권 비교 화면

- 상단에 선택한 모든 상권과 기준분기(`2025년 4분기`)를 표시합니다.
- 같은 지표를 상권별 같은 행 또는 열에 배치합니다.
- PC에서는 최대 네 상권을 한 표에서 비교하고, 좁은 모바일 화면에서는 가로 스크롤 또는 상권별 카드 전환을 사용해 값이 잘리지 않게 합니다.
- 각 지표에는 값, 단위, 상태, 근거 보기 진입점을 제공합니다.
- 비교 불가인 값은 0 대신 `비교 불가`와 사유를 보여 줍니다.
- 수치의 크고 작음만으로 추천·등급·성공 가능성을 표시하지 않습니다.

### 8.5 지도 상대 위치

- 지도 근거 카드에는 총 유동인구와 선택 업종 추정매출의 동일 자치구 내 상대 위치를 표시합니다.
- 비교군은 같은 기준분기·선택 업종의 통계 원천 행이 있는 동일 자치구 공식 상권입니다. 임의 반경을 만들어 "주변"으로 재집계하지 않습니다.
- 상대 위치는 높고 낮은 수치의 맥락일 뿐, 좋고 나쁨·창업 추천·성공 가능성을 뜻하지 않습니다.

### 8.3 근거 보기

- 지표별 근거 보기는 제공기관, 데이터셋, 수집일, 기준분기, 코드, 필터, 원천값, 계산식, 반올림을 보여 줍니다.
- 선택한 상권들의 근거가 다를 경우 각각 구분해 보여 줍니다.
- 원천 행 다운로드 기능은 원천 파일의 재배포 조건을 확인한 뒤에만 제공합니다. 1차에는 행 식별 정보 또는 요약만 제공할 수 있습니다.

### 8.4 현장 확인 질문

- 통계 지표를 보완할 질문을 분류해 표시합니다.
- 질문은 답변 입력·저장 기능 없이 읽기 전용으로 제공합니다.
- 개인 메모와 계정 기반 관심 목록 동기화는 2차 범위입니다.

## 12. 소개형 홈·비로그인 만료·계정 기록 계약 (Phase 23~28)

### 12.1 화면 진입과 재시험

- 기본 주소는 소개형 홈을 표시하며 사용 흐름을 통합합니다. 지도·긴 목록은 탐색 화면으로 분리합니다. 상세 화면 새로고침·내부 이동·인증 콜백을 일괄 홈 리다이렉트하지 않습니다.
- 마이페이지는 인증된 본인만 열 수 있습니다. 인증 확인 중 이전 계정 기록을 먼저 표시하지 않습니다. 재방문에 강제 로그아웃하지 않으며 저장 기록은 마이페이지에서 명시적으로 엽니다.
- 유효한 테스트 결과가 있으면 테스트 진입부와 마이페이지 테스트 영역에 ‘기존 테스트 결과 보기’와 ‘테스트 다시 해보기’를 나란히 표시합니다. 결과가 없을 때는 ‘테스트 시작하기’를 표시합니다.
- 재시험은 빈 답변·새 ID의 초안으로 시작합니다. 기존 답변 수정은 별도 동작입니다. 시작·취소·완료 모두 이전 결과를 삭제하거나 덮어쓰지 않으며, 완료 결과는 별도 기록입니다. 진행 중 초안이 있으면 계속하기/새로 시작을 안내하고 초안을 버릴 때만 확인합니다.

### 12.2 비로그인 임시 기록과 만료

- 보관 시간은 **마지막 실제 활동 후 60분**입니다. 30분보다 긴 작업 여유를 주는 기본값으로 선택합니다. 최초 방문부터 고정 60분이 아니므로 계속 이용하는 동안은 만료되지 않습니다.
- 범위: 테스트 답변/초안과 완료 결과 이력, 관심 상권, 생성한 후보 상권/비교 리포트, 매물 워크시트와 작성 중 입력. 만료 전 같은 브라우저 재방문·새로고침·새 탭에서도 복구합니다. 새 방문이라는 이유만으로 지우지 않습니다.
- 익명 저장에는 anonymous_session_id, record_id, schema_version, last_activity_at, expires_at을 둡니다. 만료를 검사하는 localStorage 기반 저장 계층을 사용하고 계정 캐시/인증 저장소와 명확히 구분합니다. 브라우저 자체의 저장소 삭제·차단까지 복구를 보장하지 않습니다.
- 실제 활동: 사용자의 입력·버튼 조작·페이지 이동·스크롤. 자동 API 요청, 타이머, 알림 표시, 단순 마우스 이동, 자동 새로고침은 연장 사유가 아닙니다. 이벤트 갱신은 적절히 제한하며 기록 쓰기와 만료 검사의 순서를 보장합니다.
- expires_at = last_activity_at + 60분; 현재 시각이 expires_at 이상이면 만료입니다. 앱 시작·탭 복귀·기록 읽기/쓰기·로그인 시작 시 만료를 먼저 확인하고 이후 활동을 반영합니다. 만료된 기록을 복귀 이벤트로 되살리지 않습니다.
- 열린 화면은 만료 시 개인 임시 기록과 메모리 표시를 정리하고 ‘비로그인 이용 기록이 만료됐어요’와 새로 시작을 안내합니다. 계정 저장본은 이 타이머로 삭제하지 않습니다.
- 브라우저가 닫혀 있을 때는 삭제 코드를 실행할 수 없으므로 기한이 지난 기록을 다음 실행 시 표시/이관 전에 정리합니다. 여러 탭은 같은 만료 시각과 삭제 상태를 공유하여 오래된 탭의 쓰기로 기록이 부활하지 않게 합니다.
- 임시 기록이 없으면 반복 경고는 표시하지 않습니다. localStorage.clear()로 인증 토큰이나 무관한 데이터를 지우지 않습니다.

### 12.3 로그인·만료 안내

- 첫 기록 생성 시 안내: ‘로그인하지 않으면 마지막 활동 후 1시간이 지나 이용 기록이 사라져요. 로그인하면 남아 있는 기록을 계정에 저장할 수 있어요.’
- 기록이 있는 비로그인 작업 화면에는 작은 상시 안내를 둡니다. 이용이 이어지는 동안 로그인 권유는 20분 간격으로 표시하며 동일 브라우저 여러 탭에서 중복 표시하지 않습니다.
- 만료 10분 전과 2분 전에 남은 시간과 ‘카카오로 로그인’/‘계속 이용하기’를 안내합니다. 계속 이용하기는 사용자의 명시적 활동으로 60분을 갱신합니다. 안내 표시 자체는 시간을 갱신하지 않습니다.
- 활동 중 정기 알림과 만료 예고가 겹치면 예고만 표시합니다. 숨겨진 탭에서 알림을 쌓아 두지 않으며 복귀 시 현재 상태에 맞는 안내 하나만 표시합니다. 작업을 가리는 강제 모달·반복 알럿은 사용하지 않습니다. 만료된 뒤에는 복구할 수 있는 것처럼 로그인 버튼을 설명하지 않습니다.

### 12.4 로그인 시 모든 유효 기록의 계정 이관

1. 로그인 시작 전에 만료 여부를 확인하고 아직 유효한 익명 기록 전체와 복귀 위치를 durable한 이관 대기 스냅샷으로 보존합니다. 버튼 주변에 ‘남아 있는 이용 기록을 로그인할 계정에 저장합니다’를 표시합니다. 개별 기록마다 저장을 다시 누르게 하지 않습니다.
2. 로그인 왕복 중 일반 초기화/만료 작업은 이 스냅샷을 지우지 않습니다. 인증 대기에는 시작 시점부터 최대 15분의 별도 보호 구간을 두어 만료 직전 시작한 정상 로그인을 보호합니다. 취소/실패 시 익명 이용으로 돌아가 기존 기록이 유효하면 유지하고, 남은 보관시간은 원래 만료 시각과 보호 구간 종료 중 늦은 시각까지로 안내합니다. 보호 구간까지 지나 로그인되지 않으면 다음 검사 시 만료합니다.
3. 보호 구간 안에 인증이 성공하면 스냅샷을 인증된 user.id에 귀속합니다. 인증 로딩 중 빈 배열이나 계정 조회 결과로 익명 기록을 덮어쓰지 않습니다. 최초 가입뿐 아니라 기존 계정으로 로그인할 때에도 유효 익명 기록을 추가합니다.
4. 테스트 결과 이력·생성 리포트·관심 상권·매물·초안을 모두 기존 계정 기록에 병합합니다. 상권은 코드로 중복 제거하고, 다른 테스트/리포트/매물은 ID로 구분합니다. 이름이 같아도 별도 기록은 합치지 않습니다. 동일 ID 수정 충돌은 원본을 보존한 복사본으로 처리하거나 사용자에게 선택하게 하며 조용히 덮어쓰지 않습니다.
5. batch_id와 원래 record_id로 재시도·중복 콜백·다중 탭 요청을 멱등 처리합니다. 서버는 실제 인증 사용자 소유권을 확인하고 RLS를 적용합니다. 다른 계정의 로컬 캐시를 익명 기록으로 간주하지 않습니다.
6. 서버가 해당 기록 저장을 확인한 뒤에만 그 기록의 임시본을 정리합니다. 전체 저장 확인 전에는 ‘모든 기록 저장 완료’로 표시하지 않습니다. 일부 실패하면 성공/대기 개수를 표시하고 실패분을 재시도합니다.
7. 인증 성공 후 이관 중인 기록에는 익명 만료 타이머를 적용하지 않습니다. 저장 실패·오프라인·새로고침에도 귀속된 대기본을 보존하고 같은 계정에서 재시도합니다. 로그아웃 시 화면/메모리와 일반 캐시는 정리하되 미이관 대기본은 별도 소유자 범위에 보존하여 다른 계정에 표시·자동 업로드하지 않습니다. 실제 전체 삭제/탈퇴를 선택하면 그 계정의 대기본도 정리하여 재업로드를 막습니다.

### 12.5 계정 저장 기록

- 테스트에는 답변·결과·완료 시각·질문 및 결과 규칙 버전을 보관합니다. 재시험은 새 기록이며 이전 결과는 불변입니다.
- 리포트 범위는 후보 상권 분석과 2~4곳 비교입니다. 생성 시점 입력·상권 코드/이름·업종·기준분기·출력값·결측 사유·비교군·출처·원천값·계산식·반올림·계산 버전을 함께 저장합니다. 과거 근거 보기에서 현재 데이터로 조용히 바꾸지 않습니다.
- 현재 데이터로 다시 계산은 별도 동작이며 백엔드에서 수행하고 새 결과로 저장합니다. Phase 17 리뷰 리포트는 카카오 제한 표본 수집 규칙, 공식 상권 포함 여부, 출처, 수집 시각, 전체·분석 사용 표본 수, 보관 만료 시각과 함께 별도 계정 기록으로 저장합니다. 리뷰가 1건 이상 확인되면 탐색용 주제 집계를 제공하며, 가게별 5건·3곳·30건은 충분한 표본의 기준으로 구분합니다. 5곳·50건의 전체 비교에서만 운영 아이디어를 표시합니다.
- 로그인 상태에서 새로 만드는 테스트/리포트는 ‘내 기록에 저장’으로 저장합니다. 로그인 시 익명 기록 자동 이관과 구분합니다. 관심 상권과 워크시트는 저장 상태를 표시하며 동기화합니다.
- 공통 필드: record_id, user_id, kind, title, created_at, updated_at, schema_version. 이름 변경은 표시 제목/상권 개인 별칭만 수정하고 공식 상권명·기준분기·과거 수치를 변경하지 않습니다. 세부 스키마는 Phase 25에서 확정합니다.
- 소유권은 서버/DB에서 검증하며 프런트 user_id 필터만 신뢰하지 않습니다. 인증 제공자의 이름·이메일을 제품 테이블에 중복 수집하지 않고 이메일이 없는 사용자도 식별은 user.id로 처리합니다.
- 계정 전체 기록 삭제·회원 탈퇴는 다른 기능이며 범위 안내와 확인 후 수행합니다. 카카오 계정 자체 삭제와 서비스 탈퇴도 구분합니다. 관련 서버 권한·재인증·연결 해제·실패 복구는 Phase 27에서 검증합니다.

### 12.6 기존 기록 전환과 테스트

- 기존 소유자 불명 localStorage는 자동으로 계정에 올리지 않습니다. 일회성 안내로 사용자가 본인 기록임을 확인해 가져오거나 삭제하게 합니다. 가져온 기록에는 새 임시 보관 시간을 부여합니다. 이미 계정에 귀속된 캐시는 해당 계정에서만 처리합니다.
- 시간 테스트: 59분 59초/60분 경계, 활동 연장, 안내 비연장, 숨겨진 탭/브라우저 복원, 여러 탭, 만료 후 재방문 및 쓰기 차단.
- 이관 테스트: 여러 결과·리포트·관심 상권·매물·초안 전체 보존, 만료 직전 로그인·15분 보호 경계·취소, 기존 계정 기록 유지, 중복 콜백, 부분 저장 실패, 오프라인·새로고침, 계정 전환, 이관 완료 후 임시본 정리.
- 재시험 테스트: 비로그인/로그인 각각 기존 결과 보기와 재시험, 새 초안·중단·완료 후 과거 결과 보존, 결과 별도 ID, 로그인 시 여러 결과 이관.
- SQLite로 계약/입력 검증을 수행하되 RLS는 실제 PostgreSQL의 별도 테스트 계정 A/B로 검증합니다. PC·360px에서 안내와 기록 목록·재시험 버튼을 확인합니다.

### Phase 23 적용 현황 (2026-11-03)

소개형 홈과 사용 흐름 통합, 별도 상권 탐색과 단순 메뉴를 구현했습니다. 기본 주소와 #home은 홈, #explore는 탐색입니다. 이전 #top/#explorer-title/#favorites-title은 탐색 호환 경로이며 #workflow는 홈 사용 방법 영역입니다. 홈에서는 지도 SDK와 상권 데이터 조회를 시작하지 않고 정보 구성 예시만 표시합니다. 로고는 홈, 관심 목록·탐색 복귀 링크는 해당 도구로 이동합니다. 이후 Phase 24~28도 완료했으며 검증·제약은 plan.md의 Phase별 실행 기록에 남깁니다.

## 13. 전체 업종 확장 계약 (Phase 29~33 완료)

- 기준분기 `20254`의 공식 점포 원천 100개 업종을 탐색 대상으로 삼습니다. 추정매출 원천은 62개 업종이므로 38개 업종의 매출·매출 파생지표는 `unavailable`과 원천 행 부재 사유를 반환합니다. 원천을 받지 않은 업종의 값이나 리뷰 수를 0으로 대체하지 않습니다.
- 모든 계산은 `(quarter_code, trade_area_code, industry_code)` 논리 키를 사용합니다. 인구는 같은 분기·상권 코드로 결합하되 업종별 고객 수로 명명하지 않습니다. API 응답과 저장 리포트에는 선택 업종 코드·명칭, 기준분기, 원천 행 상태, 계산 버전을 포함합니다. 서로 다른 업종을 하나의 상권 비교 요청에 섞지 않습니다.
- 가게 검색은 카카오 장소의 ID·이름·주소·위도·경도·분류를 결과별로 유지합니다. 결과 클릭은 위치 확인 지도만 갱신하고, 사용자의 확인 전에는 공식 상권 판별·리뷰 수집을 시작하지 않습니다. 좌표가 유효하지 않거나 서울 범위 밖이면 명확한 사유를 표시합니다.
- 서울시 공식 업종 코드와 카카오 장소 분류의 대응표는 원천/검증 결과와 버전을 기록합니다. 서버는 내 가게와 비교군의 업종·좌표·중복을 검증하며 불명확한 분류를 동종으로 간주하지 않습니다. 리뷰 결과에는 업종 코드, 비교군 선정 근거, 수집 시각·출처·전체/분석 표본 수·만료 시각을 포함합니다.
- 개업 후 내 가게 비교와 창업 전 상권 리뷰 집계는 목적·응답 형식·설명을 구분합니다. 사용자가 분석 버튼을 누를 때마다 새로 수집하며 같은 달 표본을 재사용하지 않습니다. 한 번에 최대 10곳·가게당 공개 화면에서 확인되는 텍스트 리뷰 최대 40건, 90일 암호화 보관, 내 가게 비교군 A~I·상권 표본 A~J 익명화를 적용합니다. 같은 대상의 이전 암호문은 신규 수집 성공 시 교체하며 과거 집계 결과는 별도 계정 기록으로 보존합니다. 검증된 동종 가게가 1곳이면 수집하고, 공개 텍스트 리뷰가 1건 이상이면 실제 관찰된 주제만 탐색용으로 표시합니다. 내 가게나 주변 한쪽에만 리뷰가 있으면 비교 결론을 표시하지 않습니다. 공개 텍스트 리뷰가 0건이면 주제 집계 대신 이유와 수집 상태를 표시합니다. 업종별 일반화가 확인되지 않은 리뷰 주제는 표시하지 않습니다.
- `GET /api/v1/review-industry/{code}`는 공식 업종명에 대응할 카카오 분류 검색어·제외어를 제공하며, `POST /api/v1/captured-review-report`와 `POST /api/v1/area-review-report`는 서버의 카카오 REST 장소 ID·좌표·분류 재확인을 거친 뒤에만 수집합니다. 상권 경로는 공식 경계 안 동종 가게 최대 10곳을 A~J로 표시하고 집계 주제만 반환합니다. 장소 검색·리뷰 수집 실패, 분류 불명, 표본 부족은 각각 이유를 표시합니다.
