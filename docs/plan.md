# 골목 레이더 구현 PLAN

## 2026-11-03 개편 계획 — 소개형 홈과 마이페이지

이번 개편은 이 PLAN에서 직접 관리합니다. 저장·만료·계정 이관 계약은 `spec.md` 12절, 제품 화면 요구는 `prd.md` 11절에 정의합니다. 별도 계획 문서는 사용하지 않습니다. Phase 22A(카카오 로그인)와 23~28은 구현과 검증을 마쳤습니다.

최신 정책: 기본 주소는 소개형 홈으로 열고, 비로그인 기록은 새 방문에 즉시 지우지 않고 **마지막 실제 활동 후 60분** 동안 보관합니다. 새로고침·재방문에서도 만료 전 기록은 복구합니다. 로그인 시 남은 테스트 결과·리포트·관심 상권·매물·초안을 계정 기존 기록과 자동 병합하며 저장 확인 전 임시본을 지우지 않습니다. 기존 결과 보기와 재시험 버튼을 나란히 제공합니다. 기존 MVP의 브라우저 영구 저장은 이 계약으로 대체하되 지표·출처·계산 계약은 유지합니다.

기존 코드에서 계정 동기화 대상은 관심 상권·워크시트였으며 테스트 이력과 리포트 보관은 Phase 25~26에서 확장했습니다. 사용자가 운영 프로젝트의 카카오 자동 로그인 뒤 ‘로그아웃’ 표시와 ‘내 기록’ 진입을 확인했습니다. 이후 실제 계정에서 기록 전체 삭제와 회원 탈퇴(Phase 27, 2026-11-05), 실행별 리뷰 결과의 계정 저장(Phase 35·37, 2026-11-08)을 확인했습니다. 기록 이름 변경은 모의 계정에서만 확인했으므로 Phase 38 회귀 점검에서 실제 계정으로 확인합니다. 관련 미커밋 변경을 점검하고 기존 작업을 덮어쓰거나 무관한 파일을 함께 커밋하지 않습니다.

### Phase 29 — 전체 업종 원천 검증·적재

**완료 기록 (2026-11-05):** 원천 논리 키 중복·업종명 불일치·공식 상권 밖 코드·빈 필수값을 적재 전에 거부하도록 했습니다. SQLite 신규/재적재와 관심 상권 참조 보존 테스트를 통과했습니다. 운영 DB는 점포 75,985행·매출 21,333행, 업종 100/62개로 적재했으며 카페 1,518/1,069행의 원천 컬럼 전체와 공식 상권 1,650곳을 보존했습니다. `/industries`가 업종별 점포/매출 보유 상권 수와 매출 원천 여부를 반환하며 운영 응답 100개 중 38개는 매출 원천이 없습니다. 백엔드 pytest 85개, 프런트 Vitest 63개와 빌드가 통과했습니다. 상세 원천·적재 결과는 `docs/data_sources.md`에 기록했습니다.

1. `database/raw/`의 2025년 점포·추정매출 파일을 원본 그대로 사용하여 20254의 업종 코드/명칭 목록, 상권 코드 교집합, 결측, `(quarter_code, trade_area_code, industry_code)` 중복을 검증합니다. 현재 확인한 20254 원천은 점포 100개, 매출 62개 업종이며 교집합 62개입니다.
2. 적재 스크립트의 카페 전용 필터를 업종 전체로 확장하고 기존 인구·영역 자료는 동일 분기/상권 코드로만 결합합니다. 기존 카페 행과 출처를 보존하고 테스트 DB에서 행 수·표본 손계산·재실행 멱등성을 확인한 후 운영 DB에 반영합니다.
3. 업종별 점포/매출 제공 여부를 API에 노출하되 매출 행이 없는 업종·상권을 0으로 만들지 않습니다. 원천 행 수·적재 결과·기준기간을 `docs/data_sources.md`에 기록합니다.

### Phase 30 — 상권 분석 전 기능의 업종 일관성
**완료 기록 (2026-11-05):** 업종 선택을 URL과 브라우저 설정에 유지하고, 상권 목록·지도 근거·2~4곳 비교·지표 근거·후보 계산·상권 리포트에 동일한 20254 업종 코드를 전달합니다. 기존 카페 링크는 기본 업종으로 열립니다. 매출 원천이 없는 업종은 매출을 0으로 대체하지 않으며, 같은 업종의 점포·유동인구 지표로 비교 가능한 범위만 보고합니다. 관심 상권은 업종과 무관한 공식 상권 코드로 보관하고, 다시 열 때 현재 선택 업종을 사용합니다. 백엔드 pytest 86개, 프론트 Vitest 63개, 빌드가 통과했습니다.

1. 선택 업종을 URL·API·저장 리포트까지 전파합니다. 지도/목록, 2~4곳 비교, 근거 보기, 상권 카드·후보 리포트·마이페이지 재열기가 같은 `industry_code`와 `quarter_code`를 사용하게 합니다. 기존 링크에는 카페 기본값을 유지합니다.
2. 백엔드 지표 이름·상대 위치·비교 모집단과 프런트 설명에서 카페 고정 문구를 선택 업종명으로 바꿉니다. 업종 공통인 유동인구·임대 통계는 특정 업종 고객/임대료로 표현하지 않습니다.
3. 성향 진단의 넓은 `food/retail/service` 답변과 공식 100개 세부 업종은 별도로 다룹니다. 후보 계산에 쓸 세부 업종을 사용자에게 선택받고, 해당 업종에 점포/매출 원천이 부족하면 추천값을 만들지 않고 이유를 표시합니다. 매물 워크시트·공식 지원 정보의 카페 전용 예시도 업종 공통 문구로 조정합니다.

### Phase 31 — 검색한 가게의 위치 확인
**완료 기록 (2026-11-05):** 검색 결과를 선택하면 PC에서는 결과 목록 옆, 360px 화면에서는 아래에 카카오 지도·해당 장소 마커·주소·분류를 표시합니다. 지도 로딩을 마친 뒤 위치 확인 버튼을 눌러야 공식 상권 및 주변 후보 조회가 시작됩니다. 다른 결과를 고르면 이전 상권·비교 상태를 지웁니다. 좌표 오류와 서울 밖 장소는 확인을 막습니다. Vitest 65개와 빌드가 통과했고, 실제 카카오 장소 검색으로 1280px/360px에서 확인 전 상권 카드 0개, 확인 후 상권 카드 표시, 가로 넘침 없음까지 검사했습니다.

1. 카카오 장소 검색의 카페 전용 `CE7` 필터를 제거하고 이름·주소·카카오 분류를 결과 목록에 표시합니다. 같은 이름의 지점은 주소와 지도 위치로 구분합니다.
2. 결과를 클릭하면 해당 결과의 위도·경도에 지도 마커를 놓고 PC에서는 목록 옆, 좁은 화면에서는 아래에 표시합니다. `이 위치가 맞아요` 확인 이후에만 공식 상권 경계 조회와 주변 가게 검색을 시작합니다. 다른 결과를 고르면 마커·주소·이전 상권/리포트 상태를 함께 갱신합니다.
3. 좌표 누락·서울 밖·지도 SDK 실패·동명 지점·모바일 화면을 확인합니다. 지도에는 선택한 가게의 위치만 표시하고 익명 비교군의 실제 상호는 공개하지 않습니다.

### Phase 32 — 업종별 리뷰 비교와 상권 리뷰 흐름
**완료 기록 (2026-11-05):** 100개 공식 업종에 대해 카카오 분류 검색어를 제공하고 내 가게 선택·주변 후보·서버 REST 장소 재확인·업종별 주제 집계까지 연결했습니다. 창업 전 상권 선택 경로는 공식 경계 안 동종 장소 최대 5곳을 익명 집계하며, 내 가게 비교와 캐시·계정별 신규 수집 횟수를 공유합니다. 업종·상권·월별 캐시 구분, 90일 암호화 보관, 가게당 5건/총 30건/3곳 기준과 부족 안내를 테스트했습니다. 실제 카카오 REST 장소 검증과 카페·한식 상권 검색을 1280px·360px에서 확인했습니다. 인증이 필요한 실제 리뷰 수집 버튼은 별도 계정 세션으로 추가 확인이 필요합니다.

1. 공식 업종 코드와 카카오 장소의 분류명/그룹 코드는 별개이므로 검증된 대응표를 둡니다. 업종별 키워드·분류 검색 후보를 검증하고, 불명확한 분류의 가게를 동종 비교군으로 조용히 포함하지 않습니다. 대응되지 않는 업종은 이유를 표시하고 그 업종의 비교를 보류합니다.
2. 개업 후 흐름은 확인한 내 가게와 같은 세부 업종의 주변 가게를 공식 상권 우선·경계 밖 반경 보충 순으로 고릅니다. 창업 전 흐름은 선택 상권과 업종에서 최대 5곳의 가게 표본을 모아 그 상권의 고객 반응을 집계하되 특정 가게의 성과로 설명하지 않습니다.
3. 업종과 가게 ID를 요청·캐시·리포트의 키에 포함하고 서버에서 좌표/업종/동종 후보를 다시 검증합니다. 기존 5곳·가게당 20건, 사용자별 월 제한, 90일 암호화 원문 보관/삭제, A~D 익명화, 표본 수준 표시를 유지합니다. 공통 리뷰 주제와 업종별 주제는 분리하고 업종별 표본이 부족하면 인사이트를 만들지 않습니다.

### Phase 33 — 전체 업종 검증

### Phase 36 — 리뷰 부분 실패·생성률 관측 (2026-11-08 완료)

수집기에서 한 장소의 페이지 이동이 실패해도 뒤의 장소를 계속 처리하는 자동 테스트를 추가했습니다. 상권 경로에서 3곳 중 1곳의 수집이 실패하고 다른 1곳에서 리뷰 1건을 얻으면 `limited` 탐색용 보고서를 반환하며, 실패한 익명 라벨과 수집·분석 건수를 감사 기록에 남기는 것을 확인했습니다. 검증된 장소가 0곳인 상권 요청도 `insufficient_sample` 결과로 기록합니다. 백엔드 pytest 99건이 통과했습니다.

### Phase 38 — 회귀 기준선 정리

**목표:** 다음 기능을 얹기 전에 테스트가 환경에 따라 실패하지 않게 하고, 11-09 디자인 개편을 실제 데이터 화면에서 확인합니다.

### Phase 39 — 데이터 품질 검사·갱신 파이프라인

**목표:** 새 분기 원천이 들어왔을 때 수집 → 스키마 검사 → 품질 검사 → 테스트 적재 → 검증 리포트까지 한 명령으로 확인하고, 문제가 있으면 운영 DB를 바꾸지 않게 합니다. (`확장메모` 3-4, 우선순위 1)

**시작 전 확인:** 검증 리포트를 저장할 위치(예: `reports/data_quality/`)와 운영 반영을 같은 명령의 별도 옵션으로 둘지, 별도 명령으로 분리할지 결정합니다. 새 키는 필요 없습니다.

**작업:**

1. 기존 `validate_phase1.py`·`load_data.py`의 검사를 재사용해 기준분기를 인자로 받는 점검 명령을 만듭니다. 기본 실행은 읽기·검사만 합니다(dry-run).
2. 원천 파일 목록·크기·SHA-256·받은 날짜·기준분기를 매니페스트로 기록합니다. 원천 파일 자체는 계속 Git에서 제외하고 수정하지 않습니다.
3. 검사 항목: 필수 컬럼 존재와 이름 변경, 논리 키 `(quarter_code, trade_area_code, industry_code)` 중복, 필수값 결측, 음수·범위 이탈, 공식 상권 밖 코드, 업종명 불일치, 주중+주말 매출과 총매출의 합 불일치, 이전 분기 대비 행 수 급변. 실패 항목은 행 예시와 함께 리포트에 남깁니다.
4. 통과하면 임시 SQLite에 적재해 행 수와 엑셀 손계산 기준표의 표본 지표를 다시 계산해 비교합니다.
5. 운영 반영은 사용자가 명시적으로 실행할 때만 합니다. 실패하면 운영 DB는 마지막 정상 분기를 그대로 둡니다.

**제외:** 자동 스케줄 실행(GitHub Actions 등)은 6장 범위 구분에 따라 넣지 않습니다.

**테스트:** 정상·중복 키·필수 컬럼 누락·결측·범위 이탈·합계 불일치 fixture로 각 검사가 실패를 정확히 보고하는지, 실패 시 운영 반영 단계로 넘어가지 않는지 pytest로 확인합니다. 현재 2025년 4분기 원천으로 실행해 기존 적재 결과(점포 75,985·매출 21,333·인구 1,648·상권 1,650)와 일치하는지 확인합니다.

**완료 조건:** 한 명령으로 검증 리포트가 생성되고, 현재 분기 원천이 오류 없이 통과하며, 실행 방법이 `database/README.md`와 `docs/data_sources.md`에 기록됩니다.

**실행 기록 (2026-11-10):**

- 시작 전 결정(계획의 권장안 적용): 리포트는 Git 제외 경로 `database/processed/data_quality/`에 JSON·Markdown으로 저장하고 결과 요약만 문서에 남깁니다. 운영 반영은 같은 명령의 `--apply` 옵션으로 두되, 검사 오류가 하나라도 있으면 실행하지 않습니다.
- 구현:
  - `database/scripts/raw_sources.py`: 원천 형식별 컬럼 이름을 공통 키로 바꾸는 규칙(점포 ZIP 영문 소문자, 매출 ZIP 한글, Open API 영문 대문자), ZIP·CSV 읽기, 파일 매니페스트(크기·SHA-256·수정 시각). 각 형식의 컬럼 이름은 실제 원천 파일과 Open API 샘플 응답에서 확인했습니다.
  - `database/scripts/data_quality.py`: 기준분기 인자를 받아 `영역 → 점포 → 매출 → 유동인구` 순서로 검사합니다. 같은 위반은 하나로 묶고 건수와 예시 5개를 남깁니다. 차단 오류가 없으면 임시 SQLite에 적재하고 표본 지표를 대조한 뒤 리포트를 저장합니다. 유동인구 원천이 없을 때도 오류로 보고해 반영은 막지만, 임시 적재와 점포·매출 표본 대조는 진행합니다.

- 실제 원천으로 확인한 사실 (검사 기준을 정하는 근거):
  - 2025년 4분기 매출 21,333행 전부에서 `주중 + 주말 = 당월 매출`, `시간대 매출 6개 합 = 당월 매출`이 정확히 성립합니다. 그래서 두 불일치는 오류로 둡니다.
  - 점포 원천의 개·폐업률은 `개·폐업 점포 수 ÷ 유사업종 점포 수 × 100`입니다. 유사업종 점포가 1곳인데 2곳이 폐업하면 200%가 되어 100%를 넘을 수 있습니다(20254에서 폐업률 40건, 개업률 4건). 처음에 둔 “0~100 범위” 오류 기준은 원천 정의와 맞지 않아 음수만 오류로 바꿨습니다. 정수 반올림 결과는 150,961건이 반올림과 일치하고 105건은 1포인트 이내로 달라(올림과 비슷) 반올림 방식을 단정할 수 없습니다. 그래서 1포인트 넘게 다를 때만 경고합니다. 유사업종 점포 0곳인 904건은 비율이 모두 0입니다.

- 실제 실행 결과 (`--quarter 20254`): 영역 1,650곳, 점포 75,985행(100개 업종·1,650개 상권, 이전 분기 76,169행), 매출 21,333행(62개 업종·1,565개 상권, 이전 분기 21,520행)에서 위반 0건, 경고 0건입니다. 임시 SQLite에 같은 행 수를 적재했고, 커피-음료·한식·`CS200001` 업종 표본 12건(매출 있는 상권 9건, 점포만 있는 상권 3건)에서 점포 수·추정매출·주중/주말 비중·건당 평균 결제액의 손계산과 백엔드 계산이 모두 일치했습니다. 유동인구 원천이 없어 판정은 `실패(오류 1건: population.missing_source)`이며, 이 상태로는 `--apply`가 동작하지 않습니다. 20251·20252·20253도 같은 결과(유동인구 외 위반 0건)였습니다.
- 테스트: `backend/tests/test_data_quality.py` 16개 — 정상 행, 다른 분기 행 제외, 상권 코드·결측·음수·합계 불일치(주중/주말, 시간대), 논리 키 중복, 업종명 불일치, 개·폐업률 정의, 유동인구 반올림 허용·영역 밖 행, 필수 컬럼 누락, 기준분기 행 없음, 행 수 급변 경고, 분기 계산·입력 형식, 임시 적재·표본 대조·리포트 저장, 오류 시 임시 적재·반영 차단, 유동인구 누락 시 반영 차단. 백엔드 전체 112개 통과·3개 건너뜀(유동인구 원천 필요).
- 제외: 6장 범위 구분에 따라 자동 스케줄 실행은 넣지 않았습니다. 사용법은 `database/README.md`에 기록했습니다.

### Phase 41 — 시간대별 매출 비중 지표

**목표:** 이미 받은 추정매출 원천의 시간대별 매출로 선택 업종의 시간대 매출 비중을 보여 줍니다. (`확장메모` 1-1, 우선순위 3)

**현재 상태:** `sales_metrics` 테이블에는 총매출·건수·주중·주말 매출만 있고 시간대 컬럼이 없습니다. 2024년 매출 원천에는 시간대별 건수 컬럼명 오타가 있었으므로 2025년 4분기 파일의 실제 컬럼명을 먼저 확인해야 합니다.

**시작 전 확인:** 비교표의 새 지표로 넣을지, 지도 근거 카드와 근거 보기에만 넣을지 결정합니다. 권장안은 비교표에는 6개 시간대를 하나의 묶음 지표로, 근거 보기에서 시간대별 값을 펼쳐 보이는 방식입니다.

**작업:**

1. 실제 원천 파일에서 시간대별 매출 금액 컬럼 6개의 이름·단위·구간을 확인하고 `docs/data_sources.md`에 기록합니다.
2. Alembic 마이그레이션으로 시간대 매출 컬럼을 추가하고 적재 스크립트·Phase 39 검사(시간대 합과 총매출의 차이 포함)를 갱신합니다.
3. `시간대 매출 ÷ 총매출 × 100`을 백엔드에서 계산하고, 분자·분모·반올림을 근거 보기에 노출합니다. 매출 원천이 없는 38개 업종과 매출 행이 없는 상권은 `비교 불가`와 사유를 반환합니다.
4. 유동인구 시간대 구간과 매출 시간대 구간이 같은지 확인합니다. 다르면 두 분포를 한 그래프에 나란히 두지 않습니다. 같더라도 인과관계로 설명하지 않습니다.

**테스트:** 계산식·반올림·분모 0·결측 단위 테스트, 엑셀 손계산 기준표 사례 추가, 매출 미제공 업종, PC·360px 표시를 확인합니다.

- 함께 발견한 점 (이번 범위 밖, 기록만):

  - 추천 후보의 `data_completeness`는 실제 개수와 관계없이 항상 ‘14/14’로 표시됩니다(`recommendations.py`의 `available_count` 기본값).

### Phase 42 — 비교 리포트 내보내기

**목표:** 2~4곳 비교 결과를 출처·기준분기·필터·계산식이 붙은 파일로 저장할 수 있게 합니다. (`확장메모` 3-1, 우선순위 2)

**시작 전 확인:** 내보내기 방식을 결정합니다. 권장안은 새 의존성 없이 인쇄 전용 화면과 브라우저의 ‘PDF로 저장’을 쓰는 방식입니다. 서버에서 PDF를 만들면 글꼴·배포 환경 부담이 커집니다.

**작업:**

1. 비교 화면에 ‘리포트 저장(PDF)’을 추가하고 인쇄 전용 레이아웃을 만듭니다.
2. 리포트에는 대상 상권·업종·기준분기·생성 일시, 지표별 원천값·단위·출처 데이터셋·필터·계산식·분자/분모, `비교 불가` 사유, 서비스 한계 문구를 넣습니다. 수치는 백엔드 응답을 그대로 쓰고 프론트에서 다시 계산하지 않습니다.
3. 추천·등급·성공 가능성 문구를 넣지 않습니다. 공개 링크·공유 버튼은 만들지 않습니다.

**테스트:** 2곳·4곳·결측 포함 비교의 인쇄 레이아웃, 긴 상권명 줄바꿈, 페이지 나눔, 리포트의 값이 화면 값과 같은지를 Vitest와 브라우저로 확인합니다.

**완료 조건:** PC와 360px에서 리포트를 PDF로 저장할 수 있고, 모든 지표에 출처·기준분기·계산식이 표시됩니다.

### Phase 43 — 마이페이지 기록 관리 확장

**목표:** 기록이 늘어나도 찾고 정리할 수 있게 검색·태그를 추가하고, 본인 기록을 파일로 받을 수 있게 합니다. (PRD 11절 ‘후속 검토’ 항목)

**시작 전 확인:** 폴더까지 넣을지, 검색·태그·내보내기만 할지 결정합니다. 권장안은 폴더 없이 제목 검색, 태그, JSON 내보내기만 넣는 것입니다. 내보내기 형식(JSON, CSV 또는 둘 다)도 결정합니다.

**작업:**

1. 기록 제목·유형·기준분기로 검색하고, 기존 유형 필터와 함께 동작하게 합니다.
2. `user_records`에 태그를 저장하는 마이그레이션을 추가하고, 기존 소유자 RLS 정책이 태그에도 그대로 적용되는지 확인합니다.
3. 로그인한 사용자가 본인 기록 전체를 파일로 받을 수 있게 합니다. 다른 사용자의 기록·리뷰 원문·암호화 보관본은 포함하지 않습니다.
4. 기록 전체 삭제·회원 탈퇴 시 태그도 함께 삭제되는지 확인합니다.

**테스트:** 검색·필터 조합, 태그 추가·삭제, 계정 A/B 격리(RLS), 내보내기 파일 내용, 빈 목록 안내, PC·360px를 확인합니다.

**완료 조건:** 실제 계정에서 검색·태그·내보내기가 동작하고 다른 계정의 기록이 노출되지 않습니다. `prd.md` 11절과 `spec.md` 12절을 함께 갱신합니다.

### Phase 44 — 맞히기 퀴즈·상권 대결 카드

**목표:** 발표·시연에서 쓸 수 있는 가벼운 참여 요소를 추가하되, 정답과 수치는 원천값 그대로 씁니다. (`확장메모` 3-2, 우선순위 4)

**시작 전 확인:** 퀴즈를 비교 화면 진입 전에 매번 보여 줄지, 선택해서 열게 할지 결정합니다(권장: 선택형, 건너뛰기 가능). 대결 카드에 넣을 지표 수(권장: 3~4개)를 결정합니다.

**작업:**

1. 맞히기 퀴즈: “이 상권에 ○○ 점포가 몇 개일까요?”처럼 선택 업종·기준분기의 원천값을 정답으로 씁니다. 원천 행이 없으면 문제를 내지 않습니다. 정답 화면에 출처·기준분기를 표시합니다.
2. 상권 대결 카드: 비교 중인 2곳의 지표를 나란히 보여 주는 이미지를 만들어 사용자 기기에 저장합니다. 승패·점수·등급·“이길 상권” 같은 판정은 넣지 않습니다. 카드에 출처·기준분기·“추천이 아님”을 표시합니다.
3. 공개 링크·SNS 공유 버튼은 만들지 않습니다.

**테스트:** 결측 상권의 퀴즈 제외, 카드 수치가 비교 API 값과 같은지, 판정 문구가 없는지, PC·360px 이미지 레이아웃을 확인합니다.

**완료 조건:** 퀴즈와 카드가 원천값만 사용하고 출처·기준분기를 표시하며, 범위 밖 기능을 암시하는 버튼이 없습니다.

## 3. Phase 진행 규칙

1. 한 번에 한 Phase만 구현합니다.
2. Phase 시작 전에 사용자에게 필요한 키·설정·결정을 먼저 확인합니다.
3. 비밀값은 `.env`에서만 사용하고 코드·문서·Git 출력에 남기지 않습니다.
4. 자동 테스트와 수동 확인 항목이 통과해야 완료로 표시합니다.
5. 실패한 항목을 고치는 동안 다음 Phase 기능을 미리 추가하지 않습니다.
6. Phase 완료 후 해당 작업 파일만 커밋하며, 이번 구현 과정은 사용자 요청에 따라 Phase별로 원격 저장소에 push합니다.

**선행조건:** Phase 1 완료.

**검증:** 빈 SQLite DB에 마이그레이션과 적재를 반복 실행하고, 상권·분기·업종별 행 수와 중복 여부를 검사합니다.

**완료 조건:** 새 테스트 DB에서 한 명령 흐름으로 스키마 생성과 검증된 데이터 적재를 재현할 수 있습니다.

**선행조건:** Phase 2 완료.

**검증:** 계산 단위 테스트와 데이터 조회 테스트 전체 통과.

**완료 조건:** 손계산 기준표와 pytest 결과가 모두 일치하고 반올림 규칙이 코드·SPEC과 같습니다.

### Phase 9. 창업 성향 진단

**목표:** 첫 방문 사용자가 6문항·문항당 4개 선택지로 업종 관심, 수요 선호, 운영 방식, 위험 선호를 정리합니다.

**작업:**

1. 질문·선택지·축별 점수를 버전이 있는 설정으로 관리합니다.
2. 시작, 1문항씩 응답, 이전 문항, 진행률, 결과 화면을 구현합니다.
3. 미완료 답변과 결과를 브라우저에 저장하고 초기화 기능을 제공합니다.
4. 결과를 임상·성공 진단처럼 표현하지 않고 답변 기여도를 공개합니다.
5. 사용자가 업종·예산·선호 결과를 직접 수정할 수 있게 합니다.

**검증:** 6문항 완주, 뒤로가기, 새로고침 복구, 잘못된 저장값 정리, 모바일 키보드·스크린리더 흐름을 확인합니다.

**완료 조건:** fixture 답변별 결과 축이 단위 테스트와 일치하고 사용자가 결과의 이유를 확인·수정할 수 있습니다.

### Phase 10. 조건 기반 탐색 후보 상권 2~3곳

**목표:** 진단 결과와 검증된 상권 지표를 결합해 탐색 후보를 2~3곳으로 좁힙니다.

**작업:**

1. 업종 데이터 보유, 지역, 예산 등 필수 조건을 먼저 적용합니다.
2. 지표를 비교 모집단 내 백분위로 정규화하고 버전이 있는 가중치 규칙을 작성합니다.
3. 후보별 총점과 지표별 기여도를 저장·응답합니다.
4. 비슷한 후보만 반복되지 않도록 설명 가능한 다양화 규칙을 적용합니다.
5. 후보 카드에서 조건 일치 근거·주의 신호·기준분기·데이터 완전성·근거 보기를 제공합니다.
6. 현재 데이터가 검증된 카페만 조건 기반 탐색 후보를 제공하고 다른 업종은 준비 중으로 표시합니다.

**검증:** 고정 입력의 순위와 기여도가 손계산표·pytest와 일치하며 결측 상권이 부당하게 유리해지지 않는지 확인합니다.

**완료 조건:** 어떤 답변과 수치가 후보 선정에 영향을 줬는지 사용자가 재현할 수 있습니다.

### Phase 11. 상권 확인 신호·주의 신호 리포트

**목표:** 선택한 상권의 특징을 검증된 숫자와 비교 모집단을 근거로 짧게 설명합니다.

3. 모든 문장에서 값·백분위·모집단·분기·근거 패널로 이동할 수 있게 합니다.
4. 성공 보장·과장·인과 단정 표현을 금지하는 문구 테스트를 둡니다.
5. 비교 리포트를 모바일 카드와 PC 요약 화면으로 제공합니다.

**검증:** 경계 백분위, 동점, 결측 fixture와 금지 표현 검사를 통과합니다.

**완료 조건:** 근거 없는 장단점 문장이 없고 기존 비교 API 값과 모두 일치합니다.

### Phase 12. 임대 벤치마크와 매물 연결

**목표:** 상권 결정 전에 임대 비용을 검토하되 공식 통계와 개별 실매물을 혼동하지 않게 합니다.

**작업:**

1. 한국부동산원 상업용부동산 임대동향조사의 상권별 임대료·공실률·임대가격지수 계약을 검증합니다.
2. 공식 분기 통계의 공간 단위와 골목 레이더 상권 코드 간 매핑 가능 여부를 확인합니다.
3. 보증금·월세·관리비·면적 입력 기반 고정비 시뮬레이터를 구현합니다.
4. 데이터 기준일, 표본 통계, 실제 매물 아님을 화면에 표시합니다.
5. 개별 매물은 사용자 직접 입력값과 외부 확인 링크만 제공하며, 제휴 여부와 관계없이 자동 수집·매물 목록 연결은 이번 제품 범위에서 제외합니다.

**차단 조건:** NAVER Developers 공개 API에서 부동산 매물 API가 확인되지 않았으므로 비공개 API·화면 크롤링은 구현하지 않습니다.

**완료 조건:** 공식 임대 통계, 사용자 입력 비용, 개별 매물이 시각·데이터 모델에서 명확히 구분됩니다.

### Phase 13. 창업 지원·자금 후보

**목표:** 상권을 고른 사용자가 공식 출처에서 확인할 지원사업·자금 후보 2건을 찾게 합니다.

**작업:**

### Phase 17. 리뷰 리포트 개편과 제한 표본 수집

**목표:** 사용자가 자신의 카페를 고르면 카카오 공개 리뷰의 제한 표본으로 주변 동종 가게를 자동 비교합니다. 수동 수집 표본 기록과 직접 입력한 리뷰 비교 화면은 종료합니다. 네이버 공개 화면은 파일럿 결과를 기록하되 자동 연결은 제공 경로가 확보될 때 별도 adapter로 추가할 계획이었으나 2026-11-10 계획에서 제외했습니다.

**정책 결정:** Google Maps 리뷰는 수집 대상에서 제외합니다. 카카오 리뷰는 포트폴리오 검증용 제한 표본만 다룹니다. 공개 화면에서 실행당 최대 5개 가게·가게당 최대 20개 리뷰·총 100개 리뷰로 제한합니다. 같은 가게·같은 달 보관본을 재사용하고 사용자별 신규 수집은 월 5회로 제한합니다. 로그인·CAPTCHA·차단 우회, 비공개 엔드포인트 호출, 병렬·상시 대량 수집은 하지 않습니다. 수집 코드는 비공개 저장소에서만 관리하고 원문 데이터는 Git·로그·클라이언트에 포함하지 않습니다.

**계획:**

1. **제한 수집 계약:** 카카오 공개 화면에서 사용자가 요청할 때만 시작합니다. 같은 가게·같은 달 표본 재사용과 사용자별 신규 수집 월 5회 제한을 백엔드에서 강제하고 실패 후 자동 재시도는 하지 않습니다.
2. **작은 표본:** 내 가게와 같은 상권·업종의 주변 카페를 우선하고 부족하면 반경 1.2km의 인접 카페를 보충해 최대 5개 가게를 선택합니다. 공식 상권 밖 가게는 소속 상권을 단정하지 않고 반경 기준으로 비교합니다. 가게별 최대 20개 리뷰를 수집합니다. 수집 직후 작성자명·프로필·링크·연락처·이메일·주소·직장·거주지·정확한 방문일 등 식별 또는 재식별 단서를 제거합니다.
3. **수집 기록 계약:** 서버에만 `provider`, 가게 ID, `peer_label`, 암호화한 비식별 본문, 수집 시각, 보관 만료 시각과 실패 상태를 둡니다. 제공 화면에서 일관되게 확인되지 않는 작성 월·평점은 추정하지 않습니다. 실제 비교 가게명과 A/B/C/D 매핑은 클라이언트·로그·Git에 보내지 않습니다.
4. **저장·보안:** 원문은 서버 측 암호화 저장소에만 최대 90일 보관하고, 분석 완료 뒤에는 비식별 주제 집계만 남깁니다. 키·원문·실제 상호·수집 경로는 프런트·Git·수집 로그에 남기지 않습니다.
5. **분석·표시:** Phase 34 기준으로 실제 리뷰가 1건 이상이면 주제별 관찰값을 탐색용으로 표시합니다. 내 가게와 주변 양쪽에 표본이 없으면 비교 결론은 내리지 않습니다. 가게별 5건·3곳·30건은 충분한 표본 판정 기준으로 사용하고, 적격 5곳·50건 이상일 때만 운영 점검 아이디어를 표시합니다. 수집 0건·수집 실패는 사유를 표시합니다.
6. **보관·삭제·감사:** 90일 만료 작업으로 암호화 본문을 삭제하고, 실행 시각·제공자·가게/리뷰 수·삭제 건수·실패 건수만 서버 전용 감사 기록에 남깁니다.
7. **검증:** 수집 상한·가게별 캐시 분리·비식별화·TTL·부분 실패 테스트, 서로 다른 카페 2곳의 실제 제한 수집, PC/360px 브라우저 검증을 마칩니다.

**완료 조건:** 수집은 정해진 공개 화면·표본·빈도를 넘지 않고, 각 인사이트에서 출처·표본·기간·한계·보관 상태를 확인할 수 있습니다. 실제 상호·리뷰 원문·작성자 식별 단서는 화면·Git·로그에 남지 않으며, 만료 원문은 자동 삭제됩니다.

**구현된 사용자 흐름:** 가게명을 검색해 카카오 장소 결과 중 내 가게를 고른다 → 좌표와 공식 상권 경계로 소속 또는 가까운 상권을 확인한다 → 같은 업종·같은 상권의 가까운 카페를 우선해 최대 4곳을 A/B/C/D로 선정한다(경계 밖은 반경 기준) → 최대 5곳·각 20건을 수집하거나 같은 달의 보관 표본을 재사용한다 → 적격 표본 수에 따라 전체·제한·부족 리포트를 원문 없이 표시한다. 집계 결과는 계정 기록에 저장하고 사용자 제공 리뷰 입력은 별도 보조 흐름으로 유지한다.

### Phase 19. 사용자 입력형 매물 검증 워크시트

**목표:** 상권 통계를 비교한 사용자가 직접 입력한 매물 후보와 현장·계약 전 확인 항목을 한 흐름으로 기록하고 비교할 수 있게 합니다. 이 기능은 창업 성공, 수익, 계약 안전성, 대출 승인 가능성 또는 계약 여부를 예측·판정·추천하지 않습니다.

**범위:**

1. 매물 별칭, 주소 또는 식별 가능한 위치 설명, 층수, 전용면적과 단위, 보증금, 월세, 관리비, 부가세 포함 여부 또는 확인 상태, 권리금, 중개수수료, 인테리어·설비 등 초기 비용 추정치, 선택 입력인 예상 월매출을 받습니다.
2. 초기 투입비(보증금+권리금+중개수수료+초기 비용), 월 공간비(월세+관리비), 면적당 월 공간비, 예상 월매출 입력 시에만 월 공간비÷예상 월매출 비율을 계산합니다.
3. 평일·주말과 오전·점심·저녁 관찰 시점, 보행 흐름·카페 이용 가능성, 경쟁점·좌석·대기·공실, 전면 폭·가시성·출입 동선, 설비·화장실·주차·상하차, 소음·악취·공사 제약, 건축물 용도·영업 가능 여부·임대차 특약·원상복구를 상태로 기록합니다.
4. 각 확인 항목은 `확인 완료`, `추가 확인`, `해당 없음`, `기록 없음` 중 하나로만 표시합니다. 법률·인허가·계약 관련 항목에는 공식 기관 또는 전문가 확인 권장을 표시합니다.
5. 로그인 없는 MVP에서는 브라우저 `localStorage`에만 저장하며, 서버 저장·주소 자동 조회·개별 매물 자동 수집은 추가하지 않습니다.

**계산·입력 규칙:**

- 금액 입력은 원 단위의 0 이상 정수, 면적은 0보다 큰 수와 `㎡` 또는 `평` 단위를 함께 저장합니다. `평` 입력은 표시·저장 단위를 보존하고 계산 시 `1평 = 3.305785㎡`로 환산합니다.
- 초기 투입비와 월 공간비는 모든 구성 항목이 입력됐을 때만 계산합니다. 관리비가 없거나 확인되지 않았으면 0으로 보정하지 않고 `입력 필요` 또는 `비교 불가`로 표시합니다.
- 면적당 월 공간비는 월 공간비와 전용면적·단위가 모두 유효할 때만 계산하며, 표시 단위는 `원/㎡`를 기본으로 하고 원입력 단위를 함께 표시합니다.
- 월 공간비 대비 예상 월매출 비율은 예상 월매출이 선택 입력이면서 0보다 클 때만 계산합니다. 0·누락·확인 전 예상 월매출은 `비교 불가` 또는 `입력 필요`로 표시합니다.
- 모든 계산식, 입력값, 단위, 상태와 계산 불가 사유를 화면에서 확인할 수 있게 합니다. 서비스는 예상 월매출을 추정하지 않습니다.

**차단 조건:** 외부 API 키, 매물 제휴, 주소 정규화, 법률·세무·부동산 중개 판단은 필요하지 않습니다. 다만 실매물 자동 수집, 비공개 API 호출, 화면 크롤링, 로그인 우회, 서버 저장, 주소 기반 자동 조회, 계약 적합성·법적 효력·인허가 가능 여부의 자동 판정은 이 Phase에서 구현하지 않습니다.

**사용자 준비 사항:** 없습니다. 사용자가 자신의 매물 후보와 관찰값을 직접 입력합니다. 주소는 정확한 도로명 주소가 아니라 사용자가 식별할 수 있는 위치 설명으로 충분하며 외부 전송하지 않습니다.

**테스트 기준:**

- 금액·면적·단위 입력, 수정, 삭제, localStorage 복구와 손상 저장값 정리를 확인합니다.
- 초기 투입비·월 공간비·면적당 월 공간비·월 공간비 대비 예상 월매출 비율을 정상·누락·0 분모·`평` 환산 사례의 손계산표와 단위 테스트로 대조합니다.
- 누락값이 0으로 렌더링되지 않고 `입력 필요` 또는 `비교 불가`와 사유를 보이는지 확인합니다.
- 모든 현장·계약 전 항목이 네 가지 상태만 허용하고, 법률·인허가·계약 항목에 공식 기관 또는 전문가 확인 권장이 표시되는지 확인합니다.
- PC와 360px 이상 화면에서 입력·상태 기록·매물 후보 비교·삭제 흐름을 확인합니다.

**완료 조건:** 사용자가 직접 입력한 서로 다른 매물 후보를 localStorage에서 복구하고, 입력값과 계산 근거를 확인하며, 공식 통계·R-ONE 벤치마크·사용자 입력값을 혼동하지 않고 현장·계약 전 확인 상태를 기록할 수 있습니다.

1. 홈과 전역 내비게이션에서 네 단계의 사용 흐름과 각 시작점을 보여 줍니다.

**차단 조건:** 기존 상권 비교 API, R-ONE 데이터 경계, localStorage 워크시트 계약을 바꾸지 않습니다. 추천·계약 판정·자동 매물 수집·새 외부 키·제휴를 추가하지 않습니다.

**사용자 준비 사항:** 없습니다.

**테스트 기준:** 첫 방문에서 워크플로우를 열어 네 단계와 진입점을 확인하고, 탐색·비교·워크시트·지원 정보·리뷰 준비 화면의 링크를 따라갈 수 있는지 PC와 360px 화면에서 확인합니다.

**완료 조건:** 각 화면에서 사용자가 현재 단계, 이용 가능한 기능, 다음 행동, 자동 판정하지 않는 범위를 확인할 수 있습니다.

### Phase 21. 선택 상권 지도 근거 카드

**목표:** 목록에서 선택한 공식 상권의 위치를 지도 중심으로 이동하고, 같은 기준분기의 유동인구·카페 매출 원천값과 계산 근거를 바로 확인하게 합니다. 수치로 계약·성공 여부를 판정하거나 상권을 추천하지 않습니다.

**범위:**

1. 상권 목록 카드 선택 시 해당 공식 상권의 지도 중심·강조와 선택 상태를 연결합니다.
2. 선택 카드 아래에 총 유동인구, 카페 추정매출, 주중·주말 매출 비중, 6개 시간대별 유동인구 비중을 표시합니다.
3. 시간대 막대는 상권 전체의 시간대 비중만 표현하며, 수치·기준분기·업종·계산식과 서울시 공식 원천을 함께 밝힙니다.
4. 원천 행이 없거나 분모가 0인 값은 0으로 보정하지 않고 `비교 불가`와 사유를 표시합니다.

**제외 범위와 차단 조건:** 현재 원천에는 거리별 좌표 유동량과 연령대별 유동인구가 없으므로 지도 열지도·도로별 빨강/파랑 표시·연령대 카드로 확장하지 않습니다. 새 외부 키·제휴·매물 수집·주소 자동 조회·개별 매물 판단은 필요하지 않으며 추가하지 않습니다.

**사용자 준비 사항:** 없습니다.

**테스트 기준:** 선택 API가 총 유동인구·매출·시간대 값·비율과 결측 사유를 정확히 반환하는지, 목록 선택이 지도와 근거 카드를 갱신하는지, PC와 360px 이상에서 수치·출처·제한 문구가 읽히는지 확인합니다.

**완료 조건:** 사용자가 목록에서 상권을 선택하면 위치와 공식 상권 단위 근거를 한 화면에서 확인하고, 거리별·연령대별 정보가 아니라는 데이터 경계를 알 수 있습니다.

### Phase 22A. 카카오 선택 로그인과 계정별 동기화

**목표:** 비로그인 사용자의 상권 탐색·비교 흐름을 유지하면서, 카카오 로그인 사용자가 관심 상권과 직접 입력한 매물 워크시트를 다른 기기에서도 안전하게 복구하게 합니다.

**범위:**

1. Supabase Auth의 Kakao provider로 로그인·로그아웃·세션 복구를 제공합니다.
2. 관심 상권과 매물 워크시트만 계정별로 저장하며, 이름·이메일·프로필 사진은 제품 DB에 별도로 저장하지 않습니다.
3. 기존 구현은 첫 로그인 병합을 사용합니다. Phase 25에서 매 로그인 시 아직 유효한 익명 기록을 안전하게 병합하는 계약(spec.md 12절)으로 대체하며, 다른 계정의 캐시는 가져오지 않습니다.
4. RLS 정책으로 인증된 사용자가 자신의 행만 조회·생성·수정·삭제하게 합니다.
5. 공유 링크, 주소 자동 조회, 실매물 수집, 서버 기반 계약 판정은 이 Phase에 포함하지 않습니다.

**사용자 준비 사항:** Kakao Developers 앱의 로그인 활성화·Supabase callback URL 등록과 Supabase Provider 설정, 프런트의 Supabase URL·anon key 설정이 필요합니다. 실제 키와 Client Secret은 `.env` 또는 Supabase Dashboard에만 보관합니다.

**테스트 기준:** 로그인 전 탐색, 카카오 로그인 후 세션 복구, 관심 상권·워크시트 동기화, 서로 다른 계정 간 데이터 격리, 로그아웃 이후 로컬 탐색을 확인합니다.

**완료 조건:** 비로그인 탐색이 막히지 않고, 로그인 사용자는 자신의 관심 상권·워크시트를 계정으로 복구하며 다른 사용자의 데이터를 읽거나 수정할 수 없습니다.

### Phase 22B. 업종 확장 준비와 지도 상대 위치

**목표:** 현재 검증된 카페 통계를 유지하면서, 추후 검증·적재한 다른 업종을 선택할 수 있게 하고 지도 클릭으로 공식 근거와 상대 위치를 확인하게 합니다.

**범위:**

1. 검증·적재 완료 업종을 API로 조회하고 탐색 화면의 업종 선택기에 노출합니다. 현재 데이터는 카페만 노출하며, 미검증 업종의 수치를 만들지 않습니다.
2. 지도 마커 클릭은 상권 선택·근거 카드 갱신으로 연결하고, 관심 저장과 분리합니다.
3. 카드에 점포·선택 업종 매출·유동인구 원천 행 상태를 각각 표시합니다.
4. 총 유동인구와 선택 업종 매출의 동일 자치구 공식 상권 비교군 내 상대 위치를 백엔드에서 계산하고, 비교군·한계를 함께 표시합니다.

**제외:** 임의 반경 기반 재집계, 추천 점수·등급·성공 예측, 검증 전 다른 업종 수치 표시는 추가하지 않습니다.

**사용자 준비 사항:** 없습니다.

**테스트 기준:** 적재 업종 목록만 API에 노출되는지, 지도 클릭이 선택 근거를 갱신하는지, 상대 위치가 같은 자치구의 원천 행 보유 상권만을 비교군으로 쓰는지, PC와 360px 이상에서 원천 상태 세 항목이 읽히는지 확인합니다.

**완료 조건:** 사용자가 지도에서 상권을 선택해 공식 통계·비교군·상대 위치를 확인하고, 신규 업종 적재 뒤 별도 프런트 변경 없이 선택할 수 있습니다.


기존 계획에 Phase 22가 두 개 있어 2026-11-10부터 22A(카카오 로그인)와 22B(업종 확장 준비)로 구분해 표기합니다. 새 범위는 23부터 시작합니다. 각 Phase 시작 전 필요한 키·설정·결정을 확인하고, 완료 조건·테스트가 통과한 뒤 해당 변경만 커밋합니다. 실패 상태에서 다음 Phase 기능을 추가하지 않습니다.

### Phase 23 — 소개형 홈과 탐색 화면 분리

- 구현: Home 신설, 기존 사용 흐름 통합, 탐색 페이지에서 소개 중복 제거, 메뉴 단순화. 기존 #top·#workflow·#explorer-title 링크의 호환 이동을 정의하고 내부 링크를 일괄 점검합니다.
- 준비: 새 외부 키 없음. 소개 문구와 대표 시작 버튼은 위 제안을 기본으로 사용.
- 검증: 기본 주소는 홈, 탐색·테스트·기존 비교 링크는 정상 이동, 뒤로가기·새로고침, PC·360px, 홈에서 지도 SDK가 불필요하게 로드되지 않음.
- 완료: 서비스 소개를 읽고 원하는 도구로 이동할 수 있으며 홈에 전체 지도·목록이 노출되지 않음.

### Phase 24 — 비로그인 1시간 보관과 만료 안내

- 구현: 공통 임시 저장 계층, 마지막 실제 활동 후 60분 만료, 새로고침·재방문·여러 탭 복구, 주기적 로그인 안내와 만료 예고, 로그인 직전 이관 스냅샷과 콜백 보존, 로그아웃/계정 전환 격리. 기존 기록 이전 안내. 구체적 계약은 spec.md 12절을 따릅니다.
- 준비: 현재 카카오 콜백과 Supabase 허용 리다이렉트 설정 확인. 인증 성공은 확인됐지만 변경할 경로의 허용 여부는 별도 확인.
- 검증: 가짜 시계로 59분 59초/60분 경계·실제 활동 연장·안내 자체는 연장하지 않음을 검증. 새 탭·브라우저 복원·새로고침·백그라운드 복귀·다중 탭 만료, 로그인 취소/복귀 및 만료 직전 로그인, 계정 A→로그아웃→B, 이전 계정의 늦은 응답 차단.
- 완료: 활동 중 기록이 유지되고 60분 미활동 후 비로그인 기록만 만료됩니다. 만료 전 안내와 로그인 왕복 중 기록 보호가 동작합니다. 계정 기록은 만료시키지 않습니다.

### Phase 25 — 계정 기록 저장과 과거 결과 보존

- 구현: 테스트·리포트 스키마/마이그레이션, 백엔드 저장·조회·수정·삭제 계약, RLS, 별칭 지원, 저장 시점 결과·근거 보존, 저장 요청 중복 방지, 기존 관심 상권·워크시트와 통합. 로그인 시 남아 있는 모든 비로그인 기록을 계정의 기존 기록에 자동 병합하고 서버 저장 확인 후에만 임시본을 정리합니다. 이관 상태·재시도와 계정 귀속을 구현합니다.
- 준비: 별도 Supabase 테스트 환경/두 계정으로 권한 검증 가능한지 확인. 필요한 서버 관리 키는 .env에만 설정하고 프런트에 전달하지 않음. 운영 DB 적용은 이 구현 계획 승인과 별도로 사용자 요청 범위 확인.
- 검증: SQLite에서 데이터 계약·직렬화·버전 호환·중복 저장·입력 검증. PostgreSQL에서 실제 RLS, 비로그인 차단, A가 B의 코드/ID를 넣어도 읽기·수정·삭제 불가. 기록 삭제 후 늦은 저장 요청으로 부활하지 않음. 여러 테스트 결과·후보/비교 리포트·관심 상권·매물·작성 중 초안을 모두 이관하는지, 기존 계정 기록 보존·중복 콜백·부분 실패·오프라인·새로고침·계정 전환 중 이관의 데이터 손실이 없는지 확인.
- 완료: 저장한 테스트·리포트를 새 세션에서 당시 값과 근거로 조회하고 이름 변경·삭제 가능. 비로그인→로그인 이관 후 모든 유효 기록이 계정에 남아야 하며 실제 RLS 검증 없이 완료 처리하지 않음.

### Phase 27 — 계정 관리와 삭제 수명주기

- 2026-11-05 진행: 마이페이지에 두 삭제 동작의 범위·입력 확인·취소·재인증·단계별 실패 안내를 구현했습니다. 백엔드는 Supabase Auth에서 현재 사용자와 최근 로그인(10분)을 확인하고 소유자 ID로 세 기록 테이블을 삭제합니다. 탈퇴는 기록 삭제→카카오 연결 해제→Supabase Auth 계정 삭제 순서이며, 카카오 연결이 이미 끊긴 재시도만 허용합니다. 새 Supabase Secret key와 구형 service_role 키를 서버 전용 설정으로 지원합니다.
- DB: 운영 DB에 `20261104_0007`을 적용해 세 계정 기록 테이블의 `user_id`를 `auth.users`와 외래 키로 연결했습니다. 삭제된 계정의 기존 JWT가 만료되기 전에도 기록 재생성을 막습니다. 적용 전후 기존 사용자 기록 14건 유지, RLS 소유자 조회와 타 계정 차단 확인.
- 실제 검증: 사용자가 본인 계정으로 회원 탈퇴를 완료했습니다. 첫 시도에서 Supabase 응답의 카카오 ID 필드 위치 차이로 삭제 전에 중단되어 파서를 수정했고, 다시 시도한 뒤 `auth.users`, `auth.identities`, 세 기록 테이블의 행이 모두 0건임을 확인했습니다. API의 성공 응답은 카카오 연결 해제 성공 ID를 확인한 뒤에만 반환합니다. 실제 기록 전체 삭제와 탈퇴 후 재가입은 별도로 수행하지 않았으며, 해당 분기는 자동 테스트로 검증했습니다. 테스트 환경 DB 연결은 현재 유효하지 않습니다.
- 구현: 로그인 정보·로그아웃, ‘내 기록 전체 삭제’와 ‘회원 탈퇴’ 분리, 삭제 범위 확인 UI, 중요 동작에 최근 인증 확인, 서버에서 본인 검증·삭제 처리, 카카오 연결 해제 정책 구현.
- 내 기록 전체 삭제: 테스트·관심 상권·리포트·워크시트 삭제, 계정은 유지. 저장된 목록과 작업 캐시도 정리하여 자동 재업로드를 막음.
- 회원 탈퇴: 개인 기록과 서비스 인증 계정 삭제, 로컬 인증·캐시 정리. 카카오 계정 자체 삭제와 구분하며 카카오 연결 해제까지 완료되었는지 별도 확인. 실패한 단계는 재시도 가능하게 설계하고 일부 실패를 전체 성공으로 표시하지 않음.
- 준비: 카카오 연결 해제 및 Supabase 계정 삭제의 최신 공식 지원 방식 확인, 서버용 자격증명 필요 여부 점검. 개인정보 처리 안내·삭제 안내 문구와 실제 처리 동작 일치 확인. 키나 인증 토큰을 문서·로그에 기록하지 않음.
- 검증: 재인증 실패, 취소, 중복 요청, 부분 실패, 소유자 위조, 탈퇴 후 재로그인, 다른 계정 데이터 보존. 실제 삭제 테스트는 전용 테스트 계정·데이터로만 수행.
- 완료: 사용자가 로그아웃·전체 기록 삭제·탈퇴의 차이를 이해하고 각 동작의 결과가 서버·화면에서 일치함.

### Phase 28 — 전체 흐름 검증과 문서 정리

- 2026-11-05 점검: 데스크톱에서 소개→탐색→관심 상권→2곳 비교→근거→임대·매물→창업 성향 테스트→후보 저장·복구→지원 정보→리뷰 비교→카카오 로그인 진입을 확인했습니다. 모의 계정 브라우저에서 저장 결과 열기·재시험·이름 변경 실패/재시도·개별/전체 삭제·로그아웃·탈퇴의 취소/부분 실패/완료를 확인했습니다. 360px 화면의 주요 8개 경로에서 가로 넘침이 없고 모바일 도구 메뉴가 작동했습니다. 브라우저 점검 29/29 통과, 인증 흐름 수정 후 모의 계정 점검 6/6 재통과.
- 시간·소유권 수정: OAuth 복귀가 15분 보호 시간을 지났을 때 만료된 익명 기록을 올리지 않도록 했습니다. 원래 60분 보관 시간이 남은 기록은 현재 내용으로 새 이관 스냅샷을 만듭니다. 계정 전환 시 미귀속 스냅샷의 교차 귀속을 막고, 이미 귀속된 다른 계정의 실패 대기본은 숨기되 보존합니다. 동시 탭의 60분 경계, 저장 실패 후 동일 ID 재시도, 계정 전환·삭제를 Vitest로 확인했습니다.
- 실행 결과: `python -m pytest -q -p no:cacheprovider --basetemp ...` 84개 통과, `npm test -- --run` 63개 통과, `npm run build` 통과. 비교 API의 2~4곳·중복/없는 코드·기준분기와 근거 원천값/계산식, 삭제 API의 소유권·재인증·부분 실패 테스트를 포함합니다.
- 남은 제약: 사용자가 실제 계정 탈퇴를 완료해 계정·기록 삭제는 운영 DB에서 확인했지만, 탈퇴 후 재가입과 실제 계정의 기록 전체 삭제는 자동 검증만 했습니다. 운영 배포·push는 수행하지 않았습니다. 빌드의 500KB 청크 경고와 Starlette 의존성 경고는 통과 결과에 영향이 없습니다.
- 구현/검증: 소개→비로그인 테스트/리포트/매물 기록→만료 안내→로그인→자동 이관→마이페이지→재시험→재방문→복구→변경/삭제의 전체 흐름. 네트워크 단절·저장 실패·동시 탭·다른 계정·새로고침·60분 만료·모바일 회귀 확인. 만료된 기록이 이관되지 않고 로그인 중 보호된 기록과 계정 저장본은 사라지지 않는지 확인.
- 준비: 운영 반영 시점과 기존 로컬 기록 이전 안내 확정. 배포·push·외부 설정 변경은 별도 요청이 없으면 하지 않음.
- 완료: 관련 pytest/Vitest/build 통과, PC·360px 실제 흐름 검증, 기록 소유권과 기준분기/근거 유지 확인, 실행 명령·결과·남은 제약 기록, 관련 파일만 커밋.

### 운영 기록 API 보안 보완 — 2026-11-03

- 원인: 프런트 운영 Supabase 설정이 골목 레이더 DB가 아닌 별도 프로젝트를 가리켜 `public.user_records` 스키마 캐시 오류가 발생했다. 운영 DB에는 `0005`가 적용됐지만 프런트의 대상이 달라 생긴 설정 불일치였다.
- 조치: 프런트를 골목 레이더 운영 프로젝트의 URL·publishable key로 정렬했다. Supabase Data API는 처음에 비활성화돼 있었고, 공개 스키마의 기존 통계 테이블에 RLS가 없어 그대로 켜지 않았다. `0006`에서 `alembic_version`과 공식 통계 7개 테이블에 기본 거부 RLS를 적용한 후 활성화했다. 사용자 기록 3개 테이블의 소유자 RLS 정책은 유지한다.
- 확인: 익명 publishable key로 `GET /rest/v1/user_records?select=record_id&limit=1`이 HTTP 200을 반환했다. RLS 때문에 비로그인 요청은 빈 목록만 받는다.
