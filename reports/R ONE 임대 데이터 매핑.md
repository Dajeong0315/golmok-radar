# R ONE 임대 통계는 경계를 나눈다

골목 레이더의 Phase 12는 **R-ONE 임대통계를 서울시 공식 상권 117개의 고유 임대료로 합치는 방식으로 진행하면 안 된다.** 한국부동산원의 임대료·공실률·임대가격지수는 개별 매물이나 개별 건물 값이 아니라 별도로 구획한 조사상권의 분기 표본통계이며, 현재 공개 API 계약에는 서울시 `TRDAR_CD`와 연결할 공통 코드·좌표·경계가 없다. 따라서 `상권별 정확 조인`은 **NO-GO**, 원천 공간 단위와 경계 불일치를 밝힌 `별도 임대시장 참고 벤치마크`는 **CONDITIONAL GO**로 판정한다. 자동 연동은 R-ONE 로그인 후 받은 인증키를 FastAPI 서버에서 사용해야 하며, 키가 있어야 전체 통계표·분류·항목 코드와 성동구·광진구 관련 범위를 검증할 수 있다. 공개 실매물 API는 확인되지 않았지만, 현재 계획은 정식 제휴가 없을 때 외부 링크를 허용하므로 실매물 제휴는 Phase 12 완료의 필수 조건이 아니다. 다음 단계는 사용자가 R-ONE Open API 인증키를 발급하고, 서비스가 서버 어댑터·출처 계약·매핑 수준·결측 사유를 구현하는 것이다.

## R-ONE은 매물이 아니라 분기 표본 벤치마크다

한국부동산원의 상업용부동산 임대동향조사는 오피스와 상가를 대상으로 **임대료·공실률·임대가격지수·투자수익률을 전국·시도·자체 조사상권 단위로 분기 공표**한다. 상가 임대료는 1층 기준 `환산임대료 / 임대가능면적`이며 환산임대료에는 보증금 전환액과 월 임대료가 들어가지만 관리비와 부가가치세는 제외된다. 즉 카페 후보 매물의 호가가 아니라 표본을 가중 집계한 시장 맥락값이다. 화면에는 `개별 매물 아님`, `표본조사`, `건물유형`, `1층 환산임대료`, `관리비·부가세 제외`, `기준분기`, `단위`를 함께 표시해야 한다. ([한국부동산원 조사개요](https://www.reb.or.kr/reb/cm/cntnts/cntntsView.do?cntntsId=1049&mi=10335&statId=S237220284))

현재 정식 자동 연동 경로는 과거 공공데이터포털의 개별 API가 아니라 **R-ONE REST Open API**다. 기존 부동산 통계 9종 API는 R-ONE 개편에 따라 종료됐고, 새 API는 `STATBL_ID`, `CLS_ID`, `ITM_ID`, 기간, 주기, 인증키 등을 받아 통계값을 반환한다. 인증키가 없는 sample 응답은 일부 행만 제공하므로 연결 확인 외 용도로 사용할 수 없다. API는 CORS와 JSONP를 지원하지 않아 브라우저에서 직접 호출할 수 없으며, 키를 백엔드 `.env`에 둔 FastAPI 어댑터가 호출해야 한다. ([R-ONE 대체 서비스 안내](https://www.reb.or.kr/reb/na/ntt/selectNttInfo.do?mi=10251&nttSn=98700)) ([R-ONE Open API 개발가이드](https://www.reb.or.kr/r-one/portal/openapi/openApiDevPage.do))

2026년 통계는 과거 계약을 그대로 재사용하기에도 부적합하다. 1분기부터 일반상가 통합 공실률과 1층 공실률이 추가됐고, 2분기 표본 재설계로 임대가격지수 기준시점과 일부 권역이 바뀌었다. 어댑터는 통계표·분류·항목 ID를 코드에 흩어 놓지 말고 설정으로 관리하며, 원천 행마다 기술문서 버전·분기·건물유형·단위·표본 개편 여부를 기록해야 한다. ([R-ONE 통계조회 안내](https://www.reb.or.kr/r-one/portal/stat/multiStatPage.do))

## 117개 서울 상권과 정확 조인은 NO-GO다

두 기관이 말하는 `상권`은 같은 공간이 아니다. 한국부동산원은 상가 집중도, 공간 분포, 조사자 의견과 상권 활성화 등을 종합해 조사 목적의 상권을 자체 구획한다. 서울시는 별도의 `TRDAR_CD`와 EPSG:5181 SHP 폴리곤을 사용한다. R-ONE 공개 API는 통계표·분류·항목 ID와 명칭을 제공하지만, 확인된 계약에는 재사용 가능한 조사상권 좌표·폴리곤·서울시 공통 코드가 없다. 서울시 영역 데이터는 폴리곤을 제공하지만 상대편 경계가 없으므로 코드 조인, 면적 중첩, 중심점 포함 또는 최근접 매칭을 검증할 수 없다. ([한국부동산원 조사 설계](https://www.reb.or.kr/reb/cm/cntnts/cntntsView.do?cntntsId=1049&mi=10335&statId=S237220284)) ([서울시 영역-상권](https://data.seoul.go.kr/dataList/OA-15560/A/1/datasetView.do))

이름 조인도 안전하지 않다. 골목 레이더에는 `건대입구역(건대)`, `건대입구역 1번`, `건대입구역 6번`처럼 동일 생활권에 속하지만 코드가 다른 서울시 상권이 존재한다. R-ONE의 한 조사상권 값을 이름 유사도만으로 세 코드에 복제하면, 하나의 표본 벤치마크가 세 상권의 독립 임대료처럼 보이게 된다. 현재 허용할 수 있는 연결은 모든 후보에 `서울 전체 참고치`를 보여 주는 `administrative_context`, 또는 전체 R-ONE 분류를 확인하고 수동 검토 근거를 남긴 다대다 `curated_rone_context`뿐이다. 후자도 `경계가 다를 수 있음`과 `contextual` 신뢰도를 항상 노출해야 하며 `exact`라고 부르면 안 된다.

| 매핑 방식 | 현재 판정 | 표시 계약 |
| --- | --- | --- |
| 공통 코드 조인 | NO-GO | 공통 공식 코드가 확인되지 않음 |
| 폴리곤 중첩 | 보류 | R-ONE 공식 경계·재사용 권한 필요 |
| 중심점·이름 최근접 | 금지 | 공간 동일성을 증명하지 못함 |
| 서울 시도 참고값 | 가능 | 개별 상권값이 아닌 광역 시장 맥락으로 표시 |
| 수동 검토 R-ONE 조사상권 | 조건부 가능 | 다대다 공유 벤치마크, 경계 불일치와 근거 표시 |

서비스 계약에는 `rone_table_id`, `rone_area_id`, `rone_area_name`, `source_period`, `building_type`, `unit`, `mapping_method`, `mapping_scope`, `confidence`, `verified_at`, 원문 링크와 검토 메모가 필요하다. 동일 R-ONE 값이 여러 `TRDAR_CD`와 관련되면 각 상권 행에 복제하지 말고 하나의 **공유 벤치마크 카드**와 연결 상권 목록으로 보여 줘야 한다. RSE 또는 표준오차가 제공되는 지표는 함께 표시하고, 미제공 값은 0이 아니라 `비교 불가`와 사유로 반환해야 한다.

## 실매물 없이도 Phase 12는 완료할 수 있다

현재 코드는 사용자 입력 보증금·월세·관리비·면적·예상매출로 월·연 공간비와 면적당 비용을 계산하고, 공식 통계와 실매물 패널을 시각적으로 분리한다. 그러나 `rent-benchmark` API는 수치 대신 `mapping_required`만 반환해 안전한 실패 상태에 머물러 있다. 이는 잘못된 값을 노출하지 않는다는 점에서는 옳지만, 기준분기·단위·R-ONE 공간 식별자·매핑 방식·신뢰도를 담는 응답 계약과 실제 공식 벤치마크가 아직 없다는 뜻이다. ([현재 rent-benchmark API](https://github.com/Dajeong0315/golmok-radar/blob/c0efae7/backend/app/main.py#L189-L204)) ([현재 임대 화면](https://github.com/Dajeong0315/golmok-radar/blob/c0efae7/frontend/src/RentPage.tsx#L37-L52))

2026년 10월 30일 기준 NAVER Developers의 공식 공개 API 목록에는 부동산 실매물 API가 없다. 네이버 검색 API나 내부 웹 요청을 매물 DB로 전용하는 것은 공개 API 목적과 지역정보 저장 제한에 맞지 않는다. 국토교통부 상업·업무용 API는 과거 **매매 실거래가**, 소상공인 상가정보 API는 **영업 업소 현황**이므로 현재 월세·보증금 실매물의 대체재가 아니다. 따라서 비공개 엔드포인트 호출이나 화면 크롤링 없이 네이버 부동산 외부 링크와 사용자 직접 입력을 유지하는 현재 동작이 가장 방어 가능하다. ([네이버 공개 API 목록](https://developers.naver.com/products/intro/plan/plan.md)) ([NAVER API 서비스 이용약관](https://developers.naver.com/products/intro/terms/terms.md)) ([국토교통부 상업업무용 매매 실거래가](https://www.data.go.kr/data/15126463/openapi.do))

Phase 12 계획은 정식 제휴·라이선스 API가 있을 때만 실매물 어댑터를 연결하고, 없으면 외부 링크를 제공하도록 이미 정했다. 그러므로 **실매물 제휴 부재는 완료 차단 조건이 아니다.** 현 MVP는 `사용자 입력 비용 + 별도 공간 단위의 공식 통계 벤치마크 + 외부 실매물 확인 링크`로 완료할 수 있다. 향후 공급자가 생기면 서면 계약에서 필드, 인증 방식, 비용, 갱신주기, 캐시·재노출 기간, 중개사·출처 표시, 만료·삭제 정책을 확인한 뒤에만 실제 매물 행을 활성화해야 한다. ([Phase 12 계획](https://github.com/Dajeong0315/golmok-radar/blob/c0efae7/docs/plan.md#L300-L314))

## 인증키 발급 뒤 네 단계로 구현한다

사용자가 준비할 것은 **R-ONE 회원 로그인과 Open API 인증키 발급** 하나다. 키는 `RONE_API_KEY` 같은 서버 전용 환경변수로 저장하고 Git·문서·로그·프런트 `VITE_` 변수에 넣지 않는다. 공개 문서에 운영 호출 한도와 캐시 조건이 충분히 명시되지 않았으므로 발급 화면의 제한과 이용조건도 함께 기록해야 한다. 인증키가 없으면 전체 분류와 성동구·광진구 관련 커버리지를 계산할 수 없고, 최신 통계표·항목·RSE 코드를 확정할 수 없다.

키 발급 후 첫 단계는 전체 통계표·분류·항목 목록과 최신 분기의 원문 응답을 `database/raw/`에 그대로 저장하고, 임대료·공실률·임대가격지수의 건물유형·단위·결측기호·표본오차를 확인하는 것이다. 두 번째 단계는 서버측 R-ONE client와 fixture parser, 재현 가능한 코드 설정을 만들고 인증키 없음·잘못된 키·최신 분기 없음·단위 변경을 테스트하는 것이다. 세 번째 단계는 `administrative_context`, `curated_rone_context`, `unavailable`을 구분하는 응답 스키마와 다대다 crosswalk를 만들되, 공식 경계가 끝내 제공되지 않으면 정확 조인을 영구 NO-GO로 고정하는 것이다. 네 번째 단계는 프런트에 기준분기·건물유형·단위·표본통계·매핑 범위·경계 경고·원문 링크를 표시하고, `건대입구` 한 값이 서울시 세 상권의 독립값으로 복제되지 않는지 PC·360px 화면과 API 테스트로 검증하는 것이다.

이 네 단계를 통과하면 Phase 12 진행표는 `비용 시뮬레이터 + R-ONE 별도 공간 참고 벤치마크 + 외부 실매물 링크`로 완료 처리할 수 있다. 반대로 이름 유사도 자동 조인, 중심점 최근접 조인, 임대가격지수를 임대료 금액으로 표시, 결측을 0으로 대체하는 구현은 즉시 실패로 판정해야 한다.

## Conclusion

Phase 12의 핵심은 더 많은 값을 붙이는 일이 아니라 **서로 다른 공간 단위를 끝까지 분리하는 일**이다. R-ONE은 후보 상권의 임대료를 정답처럼 제공하지 못하지만, 출처·건물유형·분기·단위·매핑 불확실성을 함께 보여 주면 현장 조사 전에 시장 수준을 가늠하는 유용한 첫 벤치마크가 된다.

따라서 다음 사용자 행동은 R-ONE 인증키 발급이며, 다음 개발 행동은 전체 운영 응답을 바탕으로 한 서버 어댑터와 명시적 공간 계약 구현이다. 실매물 자동 수집은 이번 Phase의 다음 순서가 아니라, 정식 제공자와 재사용 권한이 생긴 뒤 별도 어댑터로 여는 후속 경로다.
